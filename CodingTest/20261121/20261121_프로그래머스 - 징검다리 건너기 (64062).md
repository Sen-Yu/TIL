## 1. 문제 요약 및 제약 조건

### 문제 요약
- 징검다리를 건널 때마다 밟은 돌의 숫자가 1씩 감소한다.
- 숫자가 0이 된 돌은 밟을 수 없으며, 다음으로 밟을 수 있는 돌까지의 거리가 최대 $k$칸 이하일 때만 건너뛸 수 있다.
- 다음 돌까지의 거리가 $k$를 초과하면 더 이상 다리를 건널 수 없다.
- **최대 몇 명까지 징검다리를 건널 수 있는지** 구하는 문제.

### 제약 조건
- `stones` 배열의 길이: **최대 200,000 (20만)**
- 각 돌의 숫자 크기: **최대 200,000,000 (2억)**
- 건너뛸 수 있는 최대 칸수 $k$: $1 \le k \le \text{len}(stones)$

---

## 2. 고민 과정 및 코드의 발전

### ❌ 1단계: 1명씩 시뮬레이션 + 체이닝/스택 (초기 시도)
- **아이디어**: 한 사람씩 다리를 건너게 하면서 1씩 줄이고, 0이 된 돌은 스택/체이닝으로 묶어 다음 밟을 돌로 한 번에 점프시키자.
- **실패 원인 (시간 초과 TLE)**:
  - 돌의 최댓값이 **2억**이므로 사람이 최대 2억 명 건널 수 있음.
  - $20만 \times 2억 \approx 40조$ 번의 연산이 필요하여 시간 초과 발생.
  - $N$이 큰 상태에서 결괏값의 범위가 억 단위($10^8$)면 1씩 증감하는 시뮬레이션은 불가능함을 확인.

---

### ⭕ 2단계: 최종 정답 코드 (이분 탐색 / 매개변수 탐색)

```python
"""
1) 사람 한명씩
각 사람마다 체이닝 -> 콜백
stones값이 너무 큼(200,000,000) -> 시뮬레이션 손해

2) 사람 여러명 동시에 (이분 탐색)
"""
def solution(stones, k):
    answer = 0
    left = 1
    right = max(stones)  # 탐색 범위: 1명 ~ 돌의 최댓값(최대 2억)

    # number명이 건널 수 없는가? (못 건너면 True, 건널 수 있으면 False)
    def find(number):
        space = 0
        for st in stones:
            # number번째 사람이 밟으려고 할 때 이미 사라진 돌(원래 값이 number 미만)
            if st < number:
                space += 1
                if space >= k:  # 연속으로 k칸 이상 비어있으면 건널 수 없음
                    return True
            else:
                space = 0       # 밟을 수 있는 돌을 만나면 연속 빈칸 리셋

        return False

    # 이분 탐색 진행
    while left <= right:
        mid = (left + right) // 2
        
        if find(mid):
            # mid명은 못 건너므로 인원수를 줄임 (왼쪽 탐색)
            right = mid - 1
        else:
            # mid명은 건널 수 있으므로 답을 갱신하고 더 많은 인원을 시도 (오른쪽 탐색)
            answer = mid
            left = mid + 1
    
    return answer
```

## 3. 핵심 아이디어 및 원리 분석

### 💡 1. 최적화 문제를 결정 문제로 전환 (Parametric Search)
- "최대 몇 명이 건널 수 있는가?" (최적화 문제)
- ➡️ **"$M$명이 다리를 건널 수 있는가?" (Yes / No 결정 문제)**

사람 수 $M$에 대해 다리를 건널 수 있는 여부는 항상 `[가능, 가능, ..., 가능, 불가능, 불가능]`의 단조성(Monotonicity)을 띱니다. 따라서 경계선(최대 가능 인원)을 **이분 탐색(Binary Search)**으로 빠르게 찾아낼 수 있습니다.

```text
인원 수(M):   1명   2명   3명   4명   5명 ...
건널 수 있나?  ⭕    ⭕    ⭕    ❌    ❌
                          ▲
                    최대 3명 가능! (경계선 찾기)
```

---

### 💡 2. $M$명이 건널 수 있는지 판별하는 원리 ($O(N)$)
한 명씩 돌을 밟아가며 줄이지 않고, **"$M$번째 사람이 다리에 도착했을 때의 상태"**를 한 번에 확인합니다.

* $M$번째 사람보다 앞선 $M-1$명이 이미 돌을 밟고 지나갔습니다.
* 따라서 **원래 숫자가 $M$보다 작은 돌(`st < M`)은 이미 0 이하가 되어 사라진 돌**입니다.
* `st < M`인 돌이 **연속으로 $k$개 이상** 나타나면 다음 발판까지의 거리가 $k+1$칸 이상이 되므로 점프할 수 없습니다.

```text
예시: stones = [2, 4, 5, 3, 2, 1, 4, 2, 5, 1], k = 3

[M = 3명 검사: st < 3인 돌(1, 2) 제거]
원래 돌:   [ 2,  4,  5,  3,  2,  1,  4,  2,  5,  1 ]
M=3 상태:   X   O   O   O   X   X   O   X   O   X
                            └───┘
                         연속 2칸 꺼짐 (< k=3 이므로 건널 수 있음 ⭕)

[M = 4명 검사: st < 4인 돌(1, 2, 3) 제거]
원래 돌:   [ 2,  4,  5,  3,  2,  1,  4,  2,  5,  1 ]
M=4 상태:   X   O   O   X   X   X   O   X   O   X
                        └───┬───┘
                       연속 3칸 꺼짐! (점프 거리 4칸 필요 ❌ 탈락)
```

---

### 💡 3. (참고) 슬라이딩 윈도우 관점에서의 해석
이 문제는 **"크기 $k$인 모든 부분 구간 중 최댓값들의 최솟값"**을 찾는 문제로도 볼 수 있습니다.

- 연속된 $k$개의 돌이 전부 사라지려면, 그 $k$개 중 **가장 늦게까지 버티는 돌(구간 내 최댓값)**이 0이 되어야 합니다.
- 다리 전체에서 가장 먼저 뚫리지 않게 되는 구간(병목 구간)은 **구간 최댓값이 가장 작은 곳**입니다.
- 덱(deque)을 활용한 슬라이딩 윈도우 최댓값 알고리즘으로 $O(N)$ 풀이도 가능합니다.

## 4. 디버깅 & 실수했던 포인트 정리

1. **탐색 범위 설정**:
   - 처음에는 `right = len(stones)`로 설정했으나, 구하고자 하는 값은 돌의 개수(20만)가 아니라 **사람의 수(최대 2억)**이므로 `right = max(stones)`여야 함.
2. **이분 탐색 중간값 계산 식**:
   - `mid = right - left`는 중간값이 아니라 두 값의 **거리(차이)**를 구하는 식임.
   - 올바른 중간값 계산은 **`(left + right) // 2`**.
3. **무한 루프 방지**:
   - `left = mid`, `right = mid`로 갱신하면 범위가 줄어들지 않아 무한 루프에 빠짐.
   - 반드시 **`left = mid + 1`**, **`right = mid - 1`**로 명확히 범위를 축소해야 함.
4. **연속 빈칸 누적 조건**:
   - `st - step == 0`으로만 비교하면 이전 턴에 이미 0 이하가 된 돌을 놓침.
   - **`st < number`**로 비교해야 이전부터 밟을 수 없게 된 돌까지 정확히 셀 수 있음.

---

## 5. 복잡도 분석

- **시간 복잡도**: $O(N \log(\max(\text{stones})))$
  - 탐색 범위: $1 \sim 200,000,000 \rightarrow \log_2(2\cdot 10^8) \approx 28$회 반복.
  - 매 반복마다 $O(N)$ 검사: $28 \times 200,000 \approx 5.6 \times 10^6$번 연산.
  - 파이썬 기준 약 **0.05초** 이내에 매우 여유롭게 통과.
- **공간 복잡도**: $O(1)$
  - 추가적인 배열 생성 없이 포인터와 카운트 변수만 사용하므로 메모리 낭비가 없음.

---

## 6. 결론 및 배운 점
- 1명씩 시뮬레이션하는 방식의 한계(시간 복잡도 $O(N \times M)$)를 인지하고, **"여러 명을 한 번에 점프시키는 이분 탐색"**으로 발상을 전환하는 과정이 핵심이었다.
- "최댓값/최솟값을 구하라"는 문제에서 답의 범위가 억 단위로 매우 크다면, **결정 문제(Parametric Search)로 변환할 수 있는지** 가장 먼저 점검하자.
