# 6주차 프로그래밍 모의면접 핵심 정리 & 면접관 체크리스트

이 문서는 **면접자**에게는 프로그래밍 기초 및 소프트웨어 공학 전반의 깊이 있는 기술적 배경지식을 제공하고, **면접관**에게는 지원자의 개념 이해도와 실무 응용력을 정밀하게 검증할 수 있는 표준 체크리스트 및 꼬리 질문 가이드입니다.

### 1. 객체 지향 프로그래밍에 대해 설명하세요.
> **질문:** 객체 지향 프로그래밍에 대해 설명하세요.

**🎯 면접관 필수 체크 키워드:**
*   [ ] **OOP의 정의 및 패러다임:** 데이터(상태)와 해당 데이터를 조작하는 메서드(행위)를 '객체(Object)'라는 하나의 논리적 단위로 묶어 현실 세계의 개념을 모델링
*   [ ] **4대 핵심 특성:** 캡슐화(Encapsulation), 상속(Inheritance), 다형성(Polymorphism), 추상화(Abstraction)의 역할과 유기적 결합
*   [ ] **SOLID 5대 설계 원칙:** SRP(단일 책임), OCP(개방-폐쇄), LSP(리스코프 치환), ISP(인터페이스 분리), DIP(의존 역전)
*   [ ] **절차 지향 및 함수형 프로그래밍과의 대조:** 순차적 흐름(절차 지향) vs 불변성과 순수 함수 중심(함수형) vs 상태와 행위의 캡슐화(객체 지향)
*   [ ] **실무 트레이드오프:** 높은 유지보수성·재사용성 vs 과도한 추상화로 인한 설계 복잡도 증가 및 런타임 오버헤드

**💡 핵심 지식 포인트:**
*   **객체 지향 프로그래밍(OOP)의 심플한 정의와 핵심 목적:**
    *   **1줄 정의:** 데이터(상태)와 그 데이터를 다루는 함수(행위)를 **'객체(Object)'라는 하나의 독립된 부품으로 묶고, 객체들이 서로 메시지를 주고받으며 협력**하도록 만드는 프로그래밍 패러다임입니다.
    *   **쉽게 이해하는 레고 비유:** 프로그램을 명령어의 순차적 나열로 보지 않고, 독립적인 기능을 가진 **'레고 블록(부품)'들을 조립**하여 거대한 완성품을 만드는 방식입니다.
    *   **도입 목적 (단 2가지):**
        1.  **재사용성:** 잘 만들어진 객체(부품)를 다른 프로그램에서도 그대로 가져다 씀.
        2.  **유지보수성:** 특정 기능에 수정이 필요할 때, 다른 코드 전체를 뜯어고칠 필요 없이 해당 객체(부품)만 갈아 끼움.
*   **OOP 4대 핵심 특성 (1줄 요약):**
    1.  **캡슐화 (알약 비유):** 관련 데이터와 메서드를 하나로 포장하고, 불필요한 내부 세부는 밖에서 못 건드리게 숨김(정보 은닉).
    2.  **추상화 (자동차 페달 비유):** 복잡한 내부 엔진 원리는 감추고, 운전자에게 필요한 '가속 페달'이라는 단순한 인터페이스만 보여줌.
    3.  **상속 (유전 비유):** 부모 클래스의 검증된 속성과 기능을 그대로 물려받아 중복을 제거 (단, 실무에서는 결합도를 낮추기 위해 **'상속보다는 합성'** 선호).
    4.  **다형성 (리모컨 전원 버튼 비유):** '켜져라'라는 동일한 버튼(명령)을 눌러도 TV냐 에어컨이냐에 따라 각자 자기 방식대로 동작함 (오버라이딩, 오버로딩).
*   **다형성을 실현하는 두 핵심 축: 오버라이딩(Overriding) vs 오버로딩(Overloading):**
    | 비교 항목 | **오버라이딩 (Overriding - 재정의)** | **오버로딩 (Overloading - 중복 정의)** |
    | :--- | :--- | :--- |
    | **핵심 개념** | 상위 클래스의 메서드를 하위 클래스에서 **입맛에 맞게 덮어써서 재정의** | 같은 이름의 메서드를 **매개변수(타입·개수)만 다르게 여러 개 정의** |
    | **적용 범위** | 상속 관계 (부모 - 자식 클래스 간) | 동일 클래스 내부 |
    | **시그니처 규칙** | 메서드 이름, 매개변수 개수/타입, 반환형이 **완전히 동일**해야 함 | 메서드 이름은 같지만, **매개변수의 개수나 타입이 반드시 달라야 함** |
    | **바인딩 시점** | **런타임 다형성 (동적 바인딩)** — 실행 시점 객체 타입에 따라 결정 | **컴파일타임 다형성 (정적 바인딩)** — 호출 시 넘긴 인자 타입에 따라 결정 |
    | **코드 예시** | `Animal.sound()`를 `Dog`가 `멍멍`으로 재정의 | `println(int)`, `println(String)`처럼 타입별로 구비 |
    | **언어별 차이** | 대부분의 객체 지향 언어 지원 (Python의 메서드 재정의 등) | Java, C++은 지원하나 **Python, JS는 네이티브 오버로딩 미지원** (가변인자 `*args`나 기본값 매개변수로 해결) |
*   **객체 지향 설계의 5대 원칙 (SOLID):**
    *   **SRP (Single Responsibility):** 한 클래스는 단 하나의 변경 이유(책임)만을 가져야 함.
    *   **OCP (Open-Closed):** 확장에는 열려 있어야 하고, 변경에는 닫혀 있어야 함 (인터페이스를 통한 추상화 활용).
    *   **LSP (Liskov Substitution):** 상위 타입의 객체를 하위 타입의 객체로 치환해도 프로그램의 정확성이 깨지지 않아야 함.
    *   **ISP (Interface Segregation):** 클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 작게 분리해야 함.
    *   **DIP (Dependency Inversion):** 고수준 모듈은 저수준 모듈에 직접 의존해서는 안 되며, 둘 다 추상화(인터페이스)에 의존해야 함.
*   **OOP와 대비되는 핵심 프로그래밍 패러다임 및 대표 언어:**
    1.  **절차 지향 프로그래밍 (Procedural - 대표 언어: C, Pascal, Fortran):**
        *   데이터(구조체)와 함수가 완전히 분리되어, 순차적인 명령어 실행 흐름(Top-down)에 따라 데이터를 함수에 전달하여 조작.
        *   데이터와 행위가 묶여있지 않아 시스템이 방대해질수록 유지보수 및 상태 추적이 급격히 어려워짐.
    2.  **함수형 프로그래밍 (Functional - 대표 언어: Haskell, Clojure, Erlang):**
        *   객체 내부의 가변 상태를 캡슐화하여 점진적으로 변경하는 OOP와 달리, **상태 변경을 배제하는 불변성(Immutability)**과 부작용 없는 **순수 함수(Pure Function)** 중심.
        *   동시성/병렬 처리 환경에서 락(Lock) 없이도 Race Condition을 원천 차단하여 대규모 분산 처리에 안전함.
    *   *현대 언어의 경향 (Multi-paradigm):* Python, Java(8+), Kotlin, Rust, TS 등은 거시적 시스템 뼈대는 OOP로 설계하되, 내부 비즈니스 로직과 동시성은 함수형의 불변성/람다/스트림을 적극 결합하여 활용.
*   **💡 실무 적용 팁:**
    *   OOP 설계 시 클래스를 단순 데이터 바구니(Getter/Setter만 존재하는 Anemic Domain Model)로 전락시키지 말고, 객체 스스로 자신의 데이터를 바탕으로 책임을 수행하도록 **"묻지 말고 시켜라(Tell, Don't Ask)"** 원칙을 준수해야 합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "상속(Inheritance)과 합성(Composition)의 차이점은 무엇이며, 왜 현대 소프트웨어 엔지니어링에서는 합성을 선호하나요?"**
    *   👉 **답변 포인트:** 상속은 `is-a` 관계로서 부모 클래스의 내부 구현이 자식 클래스에 노출되는 화이트박스 재사용입니다. 이는 부모의 사소한 변경이 자식 전체에 영향을 주는 **강한 결합(Coupling)**을 유발하고 캡슐화를 저해합니다. 반면 합성은 `has-a` 관계로서 객체가 다른 객체의 인스턴스를 멤버로 참조하여 인터페이스를 통해 런타임에 동적으로 조립하므로, 캡슐화를 유지하면서 유연하게 교체할 수 있는 블랙박스 재사용이 가능하기 때문입니다.
*   **Q2. "다형성(Polymorphism)을 런타임에 구현하기 위해 컴파일 언어(예: C++, Java)는 내부적으로 어떤 메커니즘을 사용하나요?"**
    *   👉 **답변 포인트:** 컴파일 시점에 호출할 함수가 결정되는 정적 바인딩과 달리, 런타임 다형성은 **동적 디스패치(Dynamic Dispatch)**와 **가상 메서드 테이블(vtable / vptr)**을 통해 구현됩니다. 객체 생성 시 각 클래스에 할당된 함수 포인터 배열(vtable)을 참조하여 실제 런타임 인스턴스의 오버라이딩된 메서드를 찾아 호출합니다.

**📚 필수 핵심 용어 해설:**
*   **오버라이딩 (Overriding):** 상위 클래스로부터 상속받은 메서드를 하위 클래스에서 동일한 시그니처로 덮어써서 재정의하는 **런타임 다형성** 기법.
*   **오버로딩 (Overloading):** 하나의 클래스 내에서 동일한 이름의 메서드를 매개변수의 타입이나 개수만 다르게 하여 여러 개 중복 정의하는 **컴파일타임 다형성** 기법.
*   **결합도 (Coupling) & 응집도 (Cohesion):** 모듈 간 상호 의존성의 정도(결합도)와 모듈 내부 요소들이 하나의 목적을 위해 긴밀히 연관된 정도(응집도). 좋은 설계는 항상 **약한 결합도(Loose Coupling)와 강한 응집도(High Cohesion)**를 지향함.
*   **가상 메서드 테이블 (vtable):** 객체 지향 언어에서 런타임에 가상 함수(다형적 메서드)의 메모리 주소를 찾아 동적으로 바인딩하기 위해 유지하는 함수 포인터 테이블.

### 2. 라이브러리와 프레임웍의 차이점에 대해 설명해 주세요.
> **질문:** 라이브러리와 프레임웍의 차이점에 대해 설명해 주세요.

**🎯 면접관 필수 체크 키워드:**
*   [ ] **제어의 흐름 (Control Flow) 주체:** 애플리케이션의 전체 실행 흐름과 생명주기를 누가 통제하는가
*   [ ] **제어의 역전 (IoC, Inversion of Control):** 프레임워크의 본질적 특징으로 제어권이 프레임워크로 넘어가는 메커니즘
*   [ ] **할리우드 원칙 (Hollywood Principle):** *"Don't call us, we'll call you(우리를 부르지 마세요, 우리가 당신을 부를 겁니다)"*
*   [ ] **구체적 실무 예시:** 라이브러리(NumPy, Requests, Lodash) vs 프레임워크(Spring, Django, FastAPI)
*   [ ] **자유도와 규칙의 트레이드오프:** 호출의 유연성(라이브러리) vs 정형화된 아키텍처 규칙과 개발 생산성(프레임워크)

**💡 핵심 지식 포인트:**
*   **라이브러리와 프레임워크의 핵심 정의 및 1줄 요약:**
    *   **라이브러리 (Library):** 개발자가 전체 실행 흐름을 주도하며, 필요할 때 능동적으로 호출하여 사용하는 **'도구(Tool)'**.
    *   **프레임워크 (Framework):** 애플리케이션의 뼈대와 흐름을 쥐고 있으며, 개발자의 코드를 적절한 시점에 수동적으로 호출하는 **'틀(Architecture / Skeleton)'**.
    *   **핵심 판별 기준:** **제어의 흐름(Control Flow)을 누가 쥐고 있는가** (제어의 역전, IoC).
*   **결정적 차이점 = 제어의 역전 (IoC):**
    *   **라이브러리 (Library):**
        *   개발자가 필요에 따라 기능을 선택적으로 **직접 호출**합니다.
        *   프로그램의 전체 실행 흐름(Main 진입점, 루프, 라이프사이클)을 **개발자의 코드가 주도**합니다.
        *   도구로서 가져다 쓰며, 마음에 들지 않으면 다른 도구로 부분 교체하기가 비교적 용이합니다.
    *   **프레임워크 (Framework):**
        *   프레임워크가 전체 애플리케이션의 뼈대와 흐름을 쥐고 있으며, 특정 이벤트나 시점에 **개발자가 작성한 코드(비즈니스 로직)를 프레임워크가 호출**합니다.
        *   개발자는 프레임워크가 정의한 템플릿 메서드, 인터페이스, 애너테이션 규칙에 맞춰 빈칸을 채워 넣듯이 코드를 작성합니다.
        *   아키텍처와 생명주기 통제권이 역전되므로 이를 **제어의 역전(IoC)**이라 부릅니다.
*   **비유적 도식:**
    *   *라이브러리:* 개발자가 자동차를 직접 운전하면서, 필요할 때마다 렌치, 타이어 펌프 같은 공구를 꺼내 쓰는 형태.
    *   *프레임워크:* 정해진 레일 위를 달리는 롤러코스터에 탑승한 상태로, 프레임워크가 정해준 특정 승강장(훅, 콜백)에서만 승객(코드)이 동작하는 형태.
*   **💡 실무 적용 팁:**
    *   React의 경우 공식적으로는 "사용자 인터페이스를 만들기 위한 JS 라이브러리"를 표방하지만, 컴포넌트 라이프사이클과 렌더링 파이프라인을 React 런타임이 통제한다는 점, 그리고 Next.js 같은 메타 프레임워크와 결합되는 생태계적 특성으로 인해 실무에서는 프레임워크적 성격을 강하게 띱니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "Spring 프레임워크에서 제어의 역전(IoC)과 의존성 주입(DI)은 어떻게 연관되어 작동하나요?"**
    *   👉 **답변 포인트:** IoC는 제어의 흐름이 뒤바뀌는 설계 원칙(개념)이고, DI(Dependency Injection)는 이를 구체적으로 달성하는 디자인 패턴(구현 기법)입니다. 개발자가 객체를 `new`로 직접 생성하고 의존 관계를 맺어주지 않고, Spring의 **IoC 컨테이너**가 컴포넌트 스캔을 통해 빈(Bean) 객체의 생성, 생명주기 관리, 의존성 주입을 대신 수행함으로써 객체 간의 결합도를 낮추고 테스트 용이성을 극대화합니다.
*   **Q2. "프레임워크를 도입했을 때 발생할 수 있는 잠재적 위험이나 단점은 무엇인가요?"**
    *   👉 **답변 포인트:** 프레임워크 고유의 학습 곡선(Learning Curve)이 존재하며, 프레임워크의 규칙과 제약에 프로젝트가 강하게 종속되는 **벤더 종속(Lock-in)**이 발생합니다. 또한 세부 동작이 블랙박스화되어 런타임 버그 추적이 까다로워질 수 있고, 프레임워크 버전 업그레이드 시 대규모 Breaking Change가 발생할 리스크가 있습니다.

**📚 필수 핵심 용어 해설:**
*   **제어의 역전 (IoC, Inversion of Control):** 개발자가 작성한 프로그램이 외부 도구를 제어하던 고전적 흐름을 뒤집어, 외부 프레임워크가 개발자의 코드를 호출하고 관리하는 소프트웨어 설계 구조.
*   **할리우드 원칙 (Hollywood Principle):** 고수준 구성요소가 저수준 구성요소에 전달하는 "우리를 직접 부르지 마라, 필요할 때 우리가 당신을 부르겠다"는 프레임워크 동작 원칙.

### 3. 디자인 패턴에 대해 설명해 주세요.
> **질문:** 디자인 패턴에 대해 설명해 주세요.

**🎯 면접관 필수 체크 키워드:**
*   [ ] **디자인 패턴의 정의:** 소프트웨어 설계 과정에서 반복적으로 발생하는 문제들에 대해 검증된 재사용 가능한 객체 지향적 해결책(GoF)
*   [ ] **3대 범주 분류:** 생성(Creational), 구조(Structural), 행위(Behavioral) 패턴
*   [ ] **핵심 대표 패턴:**
    *   생성: 싱글톤(Singleton), 팩토리 메서드(Factory Method), 빌더(Builder)
    *   구조: 어댑터(Adapter), 데코레이터(Decorator), 프록시(Proxy)
    *   행위: 전략(Strategy), 옵저버(Observer), 템플릿 메서드(Template Method)
*   [ ] **도입 목적과 효과:** 개발자 간의 공통 어휘(의사소통 비용 절감), 유연한 확장성, 유지보수성 향상
*   [ ] **오버엔지니어링(Over-engineering) 경계:** 패턴을 위한 패턴 작성의 위험성과 YAGNI(You Aren't Gonna Need It) 원칙

**💡 핵심 지식 포인트:**
*   **디자인 패턴의 정의와 도입 목적:**
    *   **정의:** 소프트웨어 설계 과정에서 반복적으로 발생하는 설계 문제들에 대해, 선배 엔지니어들이 정립한 **검증되고 재사용 가능한 모범 객체 지향적 해결책(설계 템플릿)**.
    *   **도입 목적:**
        1.  **공통의 의사소통 어휘 제공:** 복잡한 설계를 "전략 패턴으로 구현하자"라는 단 한 마디로 명확히 소통하여 팀 내 커뮤니케이션 비용 대폭 절감.
        2.  **유연한 확장성 및 변경 용이성:** 모듈 간 결합도를 낮추고 응집도를 높여 요구사항 변경 시 기존 코드를 건드리지 않고 확장 가능(OCP 준수).
        3.  **검증된 신뢰성:** 수많은 실무 프로젝트에서 이미 검증된 구조이므로 아키텍처 시행착오와 잠재적 버그 최소화.
*   **GoF(Gang of Four) 3대 범주와 대표 패턴:**
    1.  **생성 패턴 (Creational Patterns):** 객체의 생성 메커니즘을 추상화하여 시스템이 인스턴스화되는 방식으로부터 독립되도록 지원.
        *   *싱글톤(Singleton):* 애플리케이션 전역에서 인스턴스를 단 하나만 생성하고 전역 접근점 제공(DB 커넥션 풀 등).
        *   *팩토리 메서드(Factory Method):* 객체 생성을 하위 클래스에 위임하여 결합도 완화.
        *   *빌더(Builder):* 복잡한 객체의 생성 과정과 표현 방법을 분리하여 동일한 생성 절차에서 서로 다른 표현 생성.
    2.  **구조 패턴 (Structural Patterns):** 클래스나 객체를 조합해 더 큰 구조를 만들면서도 유연성과 효율성을 유지.
        *   *어댑터(Adapter):* 호환되지 않는 인터페이스를 가진 두 클래스를 연결하여 협업 가능하게 변환.
        *   *데코레이터(Decorator):* 객체에 동적으로 새로운 책임(기능)을 덧붙이는 구조(기능 확장에 상속보다 유연).
        *   *프록시(Proxy):* 다른 객체에 대한 접근을 제어하기 위해 대리자 객체를 두는 구조(지연 로딩, 접근 제어, 로깅).
    3.  **행위 패턴 (Behavioral Patterns):** 객체 간의 알고리즘, 책임 분배, 제어 흐름 및 상호작용을 정의.
        *   *전략(Strategy):* 실행 중에 교체 가능한 알고리즘 군을 정의하고 캡슐화하여 클라이언트와 독립적으로 알고리즘 변경(OCP 원칙의 모범 구현).
        *   *옵저버(Observer):* 한 객체의 상태 변화가 발생하면 의존하는 모든 객체에 자동으로 알림을 전달하는 일대다 이벤트 구독 모델(Pub/Sub의 기초).
*   **[심층 집중 분석] 싱글톤 패턴 (Singleton Pattern):**
    *   **정의 및 본질:** 애플리케이션 런타임 동안 특정 클래스의 **인스턴스가 오직 1개만 생성**되도록 강제하고, 어디서든 이에 접근할 수 있는 **전역 접근점(Global Access Point)**을 제공하는 생성 패턴.
    *   **도입 이유 (핵심 장점):**
        1.  *메모리 및 생성 비용 절약:* DB 커넥션 풀, 스레드 풀, 캐시, 환경설정(Config), 로거(Logger) 등 생성 비용이 큰 객체를 매번 `new`하지 않고 1개만 만들어 재사용.
        2.  *데이터/상태의 일관성 보장:* 시스템 전역에서 하나의 단일 인스턴스 상태를 공유하여 일관된 제어 가능.
    *   **구현 핵심 3요소:**
        1.  외부에서 `new`를 호출하지 못하도록 **생성자를 `private`으로 은닉**.
        2.  클래스 내부에 단 하나의 유일한 **`private static` 인스턴스 변수** 보관.
        3.  외부에서 이 인스턴스를 가져갈 수 있는 단일 창구인 **`public static getInstance()` 메서드** 제공.
    *   **멀티스레드 환경에서의 난제와 해결 기법 (동시성 안전성):**
        1.  *단순 지연 초기화(Lazy Initialization)의 문제:* 여러 스레드가 동시에 `getInstance()`에 진입하면 인스턴스가 2개 이상 생성되는 Race Condition 발생.
        2.  *DCL (Double-Checked Locking):* 인스턴스가 `null`일 때만 `synchronized` 락 블록에 진입하고, 락 안에서 다시 한 번 `null`을 체크. 반드시 **`volatile` 키워드**를 선언해야 CPU 명령어 재정렬(Instruction Reordering)로 인한 미완성 객체 참조 버그를 방지함.
        3.  *Bill Pugh Solution (정적 내부 클래스 홀더 - 가장 권장):* `private static class LazyHolder` 내부에 인스턴스를 선언. 외부 클래스 로딩 시점이 아니라 `getInstance()`가 최초 호출될 때 JVM Class Loader 메커니즘에 의해 원자적으로 로딩되므로, 동기화 락 오버헤드 없이 완벽한 Thread-safe와 지연 로딩(Lazy Loading)을 동시 달성.
        4.  *Enum 방식 (Effective Java 권장):* JVM 레벨에서 인스턴스 1개 생성을 보장하며, 리플렉션 공격과 직렬화/역직렬화 공격을 원천 차단하는 가장 견고한 구현.
    *   **싱글톤이 안티패턴(Anti-pattern)으로 비판받는 4대 이유:**
        1.  *단위 테스트의 곤란성 (Testability 저해):* 전역 상태를 공유하므로 테스트 격리가 불가능(한 테스트의 변경이 다른 테스트에 영향). 인터페이스가 없으면 Mock 객체로 대체 불가.
        2.  *높은 결합도 (Tight Coupling):* 구체 클래스에 직접 의존하게 되어 DIP(의존 역전) 및 OCP(개방-폐쇄) 원칙을 위반.
        3.  *단일 책임 원칙(SRP) 위반:* 고유의 비즈니스 로직 외에 '인스턴스 생명주기 관리'라는 부가 책임까지 스스로 짊어짐.
        4.  *숨겨진 의존성:* 메서드 파라미터로 명시되지 않고 코드 내부에서 전역적으로 호출되므로 의존 관계 파악이 어려움.
    *   **현대 소프트웨어의 대안 (Spring 싱글톤 레지스트리):**
        *   개발자가 클래스를 정적 싱글톤 패턴(안티패턴)으로 작성하지 않고 평범한 POJO 클래스로 작성하되, **Spring IoC 컨테이너가 해당 객체를 '싱글톤 스코프'로 생성 및 생명주기를 전담 관리**.
        *   싱글톤의 장점(메모리 절약)은 온전히 취하면서, DIP 준수와 단위 테스트 시 Mock 주입이 완벽히 가능해져 단점을 극복함.
*   **💡 실무 적용 팁 & 안티패턴 방지:**
    *   디자인 패턴은 반드시 **"실제 해결해야 할 복잡성이나 변화의 요구사항"**이 존재할 때만 도입해야 합니다. 단순한 로직에 성급하게 여러 패턴을 중첩 적용하면 클래스 개수만 폭증하고 가독성을 해치는 오버엔지니어링(Anti-pattern)이 됩니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "싱글톤(Singleton) 패턴의 장점과, 이것이 안티패턴(Anti-pattern)으로 불리기도 하는 이유는 무엇인가요?"**
    *   👉 **답변 포인트:** 인스턴스를 1개만 유지하므로 메모리 낭비를 줄이고 전역 상태 공유가 편하다는 장점이 있습니다. 그러나 이는 객체 간의 결합도를 과도하게 높여 단위 테스트 시 **Mock 객체로 대체하거나 상태를 격리하기 어렵게(테스트 곤란성)** 만듭니다. 또한 멀티스레드 환경에서 Thread-safety를 보장하기 위해 동기화 락(Lock) 비용이 발생하므로, 현대 아키텍처에서는 정적 싱글톤 대신 DI 컨테이너(Spring의 싱글톤 스코프 등)에 의해 관리되는 방식을 지향합니다.
*   **Q2. "상태에 따라 동작을 분기하는 거대한 `if-else` 또는 `switch` 문을 리팩토링할 때 어떤 디자인 패턴을 적용할 수 있나요?"**
    *   👉 **답변 포인트:** 변경되는 알고리즘이나 비즈니스 규칙을 인터페이스 뒤로 숨기는 **전략(Strategy) 패턴**이나, 객체의 상태 변화에 따라 내부 동작을 스스로 바꾸는 **상태(State) 패턴**을 적용합니다. 각 조건별 동작을 독립된 클래스로 캡슐화함으로써 새로운 요구사항 추가 시 기존 코드를 수정하지 않고 새 클래스만 추가(OCP)할 수 있습니다.

**📚 필수 핵심 용어 해설:**
*   **전략 패턴 (Strategy Pattern):** 여러 알고리즘을 각각 하나의 클래스로 캡슐화하고, 실행 시점에 동적으로 알고리즘을 상호 교체할 수 있도록 설계하는 행위 패턴.
*   **YAGNI (You Aren't Gonna Need It):** 실제로 필요하기 전까지는 미래를 예단하여 미리 기능을 구현하거나 과도한 설계를 도입하지 말라는 소프트웨어 공학의 격언.

### 4. API rate limiting이 무엇이며, 그것의 주요 목적은 무엇인가요?
> **질문:** API rate limiting이 무엇이며, 그것의 주요 목적은 무엇인가요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **API Rate Limiting의 정의:** 클라이언트 또는 IP가 특정 시간 창(Time Window) 동안 보낼 수 있는 API 요청의 횟수를 제한하는 인프라/애플리케이션 계층의 제어 기법
*   [ ] **4대 핵심 목적:**
    1.  DoS/DDoS 공격 방어 및 시스템 과부하(Overload) 방지
    2.  특정 악성 유저의 자원 독점 방지 및 공정한 사용(Fair Usage / Noisy Neighbor 방지)
    3.  외부 유료 서드파티 API(LLM, 결제 등) 호출 폭증에 따른 인프라 비용 통제
    4.  서비스 티어링(Free vs Pro 등 요금제 모델)을 통한 수익화(Monetization)
*   [ ] **대표 알고리즘 메커니즘:** 토큰 버킷(Token Bucket), 리키 버킷(Leaky Bucket), 고정 윈도우(Fixed Window), 슬라이딩 윈도우(Sliding Window)
*   [ ] **HTTP 표준 응답:** `429 Too Many Requests`, `Retry-After`, `X-RateLimit-*` 헤더
*   [ ] **분산 환경 구현체:** Redis(인메모리 원자적 연산), Nginx, API Gateway

**💡 핵심 지식 포인트:**
*   **대표적인 Rate Limiting 4대 알고리즘 비교:**
    1.  **토큰 버킷 (Token Bucket):**
        *   일정 주기로 고정된 개수의 토큰이 버킷에 채워지며, 요청이 올 때마다 토큰 1개를 소모.
        *   토큰이 남아있다면 버킷 용량만큼의 **순간적인 버스트(Burst) 트래픽을 유연하게 수용**할 수 있어 실무(AWS, Nginx, Stripe 등)에서 가장 널리 쓰임.
    2.  **리키 버킷 (Leaky Bucket):**
        *   바닥에 구멍이 난 양동이 구조로, 요청이 FIFO 큐에 쌓이고 **항상 일정한 속도**로 요청을 흘려보냄(처리함).
        *   버스트를 완전히 제거하여 네트워크 대역폭과 트래픽을 완벽하게 평활화(Smoothing)하지만, 큐가 가득 차면 새 요청은 드롭됨.
    3.  **고정 윈도우 카운터 (Fixed Window Counter):**
        *   시간을 고정된 블록(예: 1분)으로 나누고 블록 내 요청 수를 카운트.
        *   구현이 가장 단순하나, 윈도우의 경계 시점(예: 0:59초와 1:01초 사이)에 요청이 몰릴 경우 **허용 임계치의 2배에 달하는 트래픽이 통과하는 스파이크 버스트 결함**이 발생.
    4.  **슬라이딩 윈도우 (Sliding Window Log / Counter):**
        *   요청 타임스탬프를 기록하거나 이전 윈도우와 현재 윈도우의 가중치를 계산하여, 어느 시점에 측정하더라도 롤링 타임 기준으로 정확한 제한을 적용. 고정 윈도우의 경계 문제를 완벽히 해결하지만 메모리/계산 비용이 증가.
*   **💡 실무 아키텍처 팁:**
    *   단일 서버 메모리 기반(예: 딕셔너리) 락은 분산 서버(Scale-out) 환경에서 동작하지 않습니다. 실무에서는 **Redis의 `INCR` 및 `EXPIRE` 명령어나 Lua 스크립트**를 활용하여 원자적(Atomic) 트랜잭션으로 전역 처리율 제한기를 구축합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "Rate Limit을 초과한 클라이언트에게 서버는 HTTP 스펙상 어떻게 응답해야 하며, 헤더에는 어떤 정보를 담아야 하나요?"**
    *   👉 **답변 포인트:** 서버는 **`429 Too Many Requests`** 상태 코드를 반환해야 합니다. 응답 헤더에는 클라이언트가 요청 재시도 타이밍을 알 수 있도록 **`Retry-After`**(재시도 가능한 대기 초 또는 날짜)를 포함해야 하며, 표준적으로 `X-RateLimit-Limit`(허용 한도), `X-RateLimit-Remaining`(현재 윈도우 내 남은 요청 수), `X-RateLimit-Reset`(제한이 리셋되는 Unix 타임스탬프)을 함께 전달합니다.
*   **Q2. "대규모 분산 환경에서 Redis 기반 처리율 제한기를 구현할 때 발생할 수 있는 Race Condition 문제는 어떻게 해결하나요?"**
    *   👉 **답변 포인트:** 요청 수 확인(`GET`)과 증가(`INCR`) 사이에 여러 요청이 동시 진입하면 임계치를 초과 통과시키는 동시성 버그가 발생합니다. 이를 방지하기 위해 Redis 서버 내에서 한 번에 원자적으로 실행됨이 보장되는 **Lua 스크립트**를 작성하여 실행하거나, Redis의 단일 트랜잭션 블록(`MULTI`/`EXEC`)을 사용해 격리성을 보장합니다.

**📚 필수 핵심 용어 해설:**
*   **토큰 버킷 (Token Bucket):** 고정된 속도로 토큰을 보충하고 요청마다 토큰을 차감하여, 평균 처리율을 유지하면서도 일시적인 버스트 트래픽을 안전하게 허용하는 알고리즘.
*   **Noisy Neighbor 현상:** 클라우드나 멀티 테넌트 환경에서 특정 사용자가 시스템 자원(CPU, 네트워크, DB 등)을 과도하게 독점하여 인접한 다른 선량한 사용자들의 성능을 저하시키는 현상.

### 5. 애자일 개발 방법론에 대해 설명해 주세요.
> **질문:** 애자일 개발 방법론에 대해 설명해 주세요.

**🎯 면접관 필수 체크 키워드:**
*   [ ] **애자일의 등장 배경과 패러다임:** 요구사항을 사전에 완벽히 고정하고 순차적으로 진행하던 전통적 폭포수(Waterfall) 모델의 한계 극복
*   [ ] **반복적·점진적 개발 (Iterative & Incremental):** 짧은 주기(스프린트)를 반복하며 동작 가능한 소프트웨어를 빠르게 배포하고 피드백을 수용
*   [ ] **애자일 선언문(Agile Manifesto) 4대 핵심 가치:**
    1.  프로세스와 도구보다 **개인과 상호작용**
    2.  포괄적인 문서보다 **작동하는 소프트웨어**
    3.  계약 협상보다 **고객과의 협력**
    4.  계획을 따르기보다 **변화에 대응하기**
*   [ ] **스크럼(Scrum) 프레임워크 3요소:** 역할(PO, SM, Dev Team), 이벤트(스프린트, 플래닝, 데일리 스크럼, 리뷰, 회고), 산출물(제품/스프린트 백로그)
*   [ ] **현대 엔지니어링 실천법:** CI/CD 파이프라인, 테스트 자동화, TDD와의 유기적 결합

**💡 핵심 지식 포인트:**
*   **폭포수(Waterfall) vs 애자일(Agile) 비교:**
    *   *폭포수 모델:* 요구분석 $\to$ 설계 $\to$ 구현 $\to$ 테스트 $\to$ 배포가 단방향으로 진행. 초기에 모든 스펙을 확정하므로 요구사항 변경 시 막대한 비용 발생, 프로젝트 후반부 테스트 단계에서야 결함 발견.
    *   *애자일 방법론:* 1~4주 단위의 짧은 이터레이션을 통해 소프트웨어를 점진적으로 완성. 시장과 사용자의 변화하는 요구를 즉각적으로 설계에 재반영.
*   **스크럼(Scrum)의 핵심 운영 사이클:**
    1.  **제품 백로그 (Product Backlog):** 비즈니스 가치에 따라 PO(Product Owner)가 우선순위를 매긴 요구사항 목록.
    2.  **스프린트 (Sprint):** 통상 1~2주간 진행되는 고정된 작업 이터레이션.
    3.  **데일리 스크럼 (Daily Stand-up):** 매일 15분간 어제 한 일, 오늘 할 일, 장애 요인(Impediment)을 공유하는 짧은 동기화 회의.
    4.  **스프린트 리뷰 & 회고 (Review & Retrospective):** 리뷰는 이해관계자에게 완성된 기능 데모를 시연하는 자리이고, **회고(Retrospective)**는 팀의 프로세스, 협업 방식, 도구의 개선점을 찾고 실행 가능한 액션 아이템을 도출하는 내부 성찰 회의.
*   **💡 실무 적용 팁:**
    *   애자일이 "문서화를 아예 하지 않는 것"이나 "계획 없이 주먹구구로 코딩하는 것"이라는 인식은 치명적인 오해입니다. 애자일은 불필요한 형식적 문서를 줄이고 핵심 비즈니스 가치와 엔지니어링 품질(테스트 코드, 자동화)에 집중하자는 철학입니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "애자일의 대표적인 두 갈래인 스크럼(Scrum)과 칸반(Kanban)의 가장 큰 차이점은 무엇인가요?"**
    *   👉 **답변 포인트:** 스크럼은 **1~2주의 고정된 주기(Time-boxed Sprint)**를 정해놓고 스프린트 내의 스코프 변경을 제한하며 릴리즈를 반복합니다. 반면 칸반은 정해진 스프린트 주기가 없이 지속적인 흐름(Continuous Flow)에 기반하며, 현재 진행 중인 작업의 개수를 제한하는 **WIP(Work In Progress) 제한**을 두어 병목을 시각화하고 작업의 처리 시간(Lead Time)을 최적화하는 데 중점을 둡니다.
*   **Q2. "형식적으로 스탠드업만 하고 실질적으로는 변화에 대응하지 못하는 이른바 '좀비 스크럼(Zombie Scrum)'을 극복하기 위해 가장 중요한 것은 무엇인가요?"**
    *   👉 **답변 포인트:** 단순히 스프린트 세레머니를 기계적으로 흉내 내는 것이 아니라, 스프린트 끝마다 **실제 사용자에게 가치를 전달할 수 있는 '잠재적으로 출시 가능한 제품 증분(Potentially Releasable Increment)'**을 만들어내야 합니다. 이를 뒷받침하기 위해 자동화된 빌드/테스트(CI/CD) 인프라와 스프린트 회고(Retrospective)를 통한 실제 액션 아이템의 실행이 필수적입니다.

**📚 필수 핵심 용어 해설:**
*   **스프린트 (Sprint):** 계획 수립부터 개발, 테스트, 배포 가능한 단위 산출물 완성까지를 완료하는 고정된 길이(1~4주)의 반복 주기.
*   **WIP (Work In Progress) 제한:** 칸반 보드에서 동시에 진행할 수 있는 작업의 최대 개수를 강제로 제한함으로써, 멀티태스킹 오버헤드를 줄이고 병목 현상을 빠르게 해소하기 위한 규칙.

### 6. 동기(Synchronous) 프로그래밍과 비동기(Asynchronous) 프로그래밍의 차이점에 대해 설명해 주세요.
> **질문:** 동기(Synchronous) 프로그래밍과 비동기(Asynchronous) 프로그래밍의 차이점에 대해 설명해 주세요.

**🎯 면접관 필수 체크 키워드:**
*   [ ] **동기(Sync)의 정의:** 작업을 요청한 주체가 요청받은 작업의 완료 여부를 직접 확인하고, 순차적으로 제어 흐름을 진행하는 방식
*   [ ] **비동기(Async)의 정의:** 작업을 요청한 주체가 완료 여부를 기다리지 않고 다음 작업을 즉시 수행하며, 완료 시 콜백/이벤트/Future로 결과를 통보받는 방식
*   [ ] **블로킹(Blocking) vs 논블로킹(Non-blocking)과의 엄격한 구별:**
    *   동기/비동기는 **'작업 완료 여부와 순서를 누가 신경 쓰는가'**의 관점
    *   블로킹/논블로킹은 **'호출된 함수가 제어권(Control)을 즉시 돌려주는가'**의 관점
*   [ ] **2x2 매트릭스 개념 이해:** Sync-Blocking, Sync-Nonblocking, Async-Blocking, Async-Nonblocking
*   [ ] **비동기 구현 아키텍처:** 이벤트 루프(Event Loop), 논블로킹 I/O 다중화(epoll/kqueue), 프로미스(Promise), `async/await`

**💡 핵심 지식 포인트:**
*   **동기/비동기 vs 블로킹/논블로킹의 관점 차이 및 명확한 정의:**
    *   두 개념은 자주 혼용되지만, **서로 다른 관심사(관점)를 다루는 독립된 축**입니다:
    *   **1. 동기(Synchronous) vs 비동기(Asynchronous) $\to$ '결과 처리 및 순서 관점':**
        *   **동기 (Sync):** 호출자(Caller)가 호출된 작업(Callee)의 **완료 여부와 결과를 직접 신경 쓰고 확인**하는 방식. 결과가 나올 때까지 멈춰 있거나, 주기적으로 끝났는지 확인(Polling)함.
        *   **비동기 (Async):** 호출자가 요청만 넘겨두고 **결과를 직접 챙기지 않음**. 호출된 작업이 백그라운드에서 완료되면 **콜백(Callback), 이벤트, Promise 등으로 호출자에게 결과를 통보**함.
    *   **2. 블로킹(Blocking) vs 논블로킹(Non-blocking) $\to$ '제어권(Control) 반환 관점':**
        *   **블로킹 (Blocking):** 호출된 함수가 자신의 작업이 끝날 때까지 **제어권을 넘겨주지 않고 붙잡고 있는 것**.
            *   *호출자의 상태:* 제어권을 뺏겼으므로 아무것도 하지 못하고 대기(Wait/Sleep) 상태에 머묾.
        *   **논블로킹 (Non-blocking):** 호출된 함수가 작업을 시작하자마자 **제어권을 호출자에게 즉시 반환하는 것**.
            *   *호출자의 상태:* 제어권을 바로 돌려받았으므로, 호출된 작업의 완료 여부와 무관하게 **자신의 다음 코드를 즉시 실행**할 수 있음.
*   **동기/비동기 $\times$ 블로킹/논블로킹 2x2 매트릭스 심층 분해:**
    1.  **Sync + Blocking (전통적 동기 I/O):**
        *   *동작:* 제어권을 넘겨주어 호출자가 멈추고(Blocking), 작업이 끝날 때까지 결과를 기다림(Sync).
        *   *예시:* C/Python의 기본 파일 읽기, JDBC 표준 SQL 쿼리.
    2.  **Sync + Non-blocking (폴링 모델):**
        *   *동작:* 제어권을 즉시 돌려받아 다른 일을 할 수 있지만(Non-blocking), 호출자가 루프를 돌며 "작업 다 끝났어?"라고 계속 확인(Sync).
        *   *예시:* 논블로킹 소켓에서 데이터 수신 여부를 확인하는 폴링(Polling) 루프.
    3.  **Async + Non-blocking (이상적인 모던 비동기 I/O):**
        *   *동작:* 제어권을 즉시 돌려받아 멈추지 않고(Non-blocking), 작업 완료 시 이벤트 루프나 콜백으로 결과를 받음(Async).
        *   *예시:* Node.js, Netty, FastAPI (`async def` 기반 논블로킹 네트워크 호출).
    4.  **Async + Blocking (치명적인 안티패턴):**
        *   *동작:* 비동기 형태로 콜백을 등록했으나, 내부에서 블로킹 함수가 호출되어 스레드 자체가 잠들어버림.
        *   *예시:* Node.js나 FastAPI의 `async def` 핸들러 내부에서 동기 DB 드라이버나 `time.sleep()`을 호출하여 이벤트 루프 전체를 얼려버리는 실수.
*   **비동기 I/O의 자원 효율성:**
    *   동기 블로킹 방식은 I/O(DB 쿼리, 네트워크 호출) 대기 시간 동안 스레드가 CPU를 쓰지 못한 채 잠들어 있으므로, 동시성 처리를 위해 수천 개의 스레드를 띄워야 해 **막대한 메모리 점유와 컨텍스트 스위칭 오버헤드**가 발생.
    *   비동기 논블로킹 모델은 소수의 스레드(보통 코어 수만큼)가 단일 **이벤트 루프**를 돌며 수만 개의 소켓 I/O를 다중화(I/O Multiplexing)하여 대기 시간 동안 다른 클라이언트 요청을 처리하므로 시스템 처리량(Throughput)이 극대화됨.
*   **💡 실무 적용 팁:**
    *   `async/await`는 문법적 설탕(Syntactic Sugar)으로 콜백 헬(Callback Hell)을 없애고 비동기 코드를 동기식 코드처럼 직관적으로 읽을 수 있게 해줍니다. 그러나 비동기 프레임워크 내부에서 블로킹 연산(예: `time.sleep()` 또는 대용량 파일 읽기)을 호출하면 **이벤트 루프 전체가 멈춰버리는 이벤트 루프 기아(Starvation)**가 발생하므로 주의해야 합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "CPU 바운드(연산 집중) 작업에도 비동기(async/await) 프로그래밍을 적용하면 성능이 개선되나요?"**
    *   👉 **답변 포인트:** 전혀 개선되지 않거나 오히려 오버헤드로 인해 느려집니다. 비동기 프로그래밍은 네트워크나 디스크 같은 **I/O 대기 시간(Idle Time)을 활용**하여 다른 작업을 전환 처리하는 데 특화된 기법입니다. CPU가 100% 연산에 사용되는 CPU 바운드 작업은 I/O 대기 시간이 없으므로 단일 이벤트 루프 스레드를 독점하여 다른 요청까지 마비시킵니다. CPU 바운드 작업은 비동기가 아니라 **멀티프로세싱(Multi-processing)이나 워커 스레드 풀 오프로딩**을 통해 병렬화(Parallelism)해야 합니다.
*   **Q2. "운영체제 레벨에서 수많은 비동기 네트워크 소켓 이벤트를 효율적으로 감지하기 위해 사용하는 I/O 멀티플렉싱(I/O Multiplexing) 시스템 콜은 무엇인가요?"**
    *   👉 **답변 포인트:** 고전적인 `select`나 `poll`은 파일 디스크립터(FD) 전체를 선형 탐색($O(N)$)해야 하는 한계가 있었습니다. 이를 극복하기 위해 Linux는 **`epoll`**, macOS/BSD는 **`kqueue`**를 사용합니다. 이들은 커널 레벨에서 이벤트가 발생한 소켓 FD만 $O(1)$로 알림을 전달하여, 수만 개의 동시 커넥션(C10K 문제)을 최소한의 CPU 소비로 처리할 수 있게 합니다.

**📚 필수 핵심 용어 해설:**
*   **블로킹 (Blocking):** 호출된 함수가 자신의 실행을 마칠 때까지 제어권을 독점하여, 호출한 측의 실행을 멈추게(대기) 만드는 상태.
*   **논블로킹 (Non-blocking):** 호출된 함수가 실행 직후 제어권을 즉시 반환하여, 호출한 측이 대기 없이 곧바로 다음 코드를 실행할 수 있게 하는 상태.
*   **이벤트 루프 (Event Loop):** 이벤트 큐에 쌓인 비동기 태스크와 콜백을 감시하며, 호출 스택(Call Stack)이 비었을 때 태스크를 하나씩 스택으로 끌어올려 실행해 주는 단일 스레드 기반 스케줄러.
*   **C10K 문제:** 1대의 웹 서버가 동시에 1만 개(10,000) 이상의 클라이언트 커넥션을 메모리 및 컨텍스트 스위칭 낭비 없이 효율적으로 처리하기 위한 분산/네트워크 아키텍처 도전 과제.

### 7. 프로세스와 스레드의 차이점은 무엇이며, 멀티스레딩 환경에서 주의해야 할 점은 무엇인가요?
> **질문:** 프로세스와 스레드의 차이점은 무엇이며, 멀티스레딩 환경에서 주의해야 할 점은 무엇인가요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **프로세스 (Process) 정의:** OS로부터 독립적인 자원(메모리 주소 공간)을 할당받아 실행되는 작업의 기본 단위
*   [ ] **스레드 (Thread) 정의:** 프로세스 내부에서 실행되는 흐름의 단위이자 CPU 스케줄링의 최소 단위
*   [ ] **메모리 공유 구조의 차이:**
    *   프로세스: 독립된 코드(Code), 데이터(Data), 힙(Heap), 스택(Stack) 영역 보유 (상호 침범 불가, IPC 필요)
    *   스레드: 부모 프로세스의 **Code, Data, Heap 영역을 상호 공유**하며, 각자 독립적인 **Stack과 레지스터(PC)**만 보유
*   [ ] **컨텍스트 스위칭 오버헤드 비교:** 프로세스는 가상 메모리 매핑 교체(MMU/TLB 플러시)로 무거움 vs 스레드는 캐시 보존 및 스택/레지스터 교체로 가벼움
*   [ ] **멀티스레딩 환경 3대 주의점:** 경쟁 상태(Race Condition), 교착 상태(Deadlock), 스레드 안전성(Thread-Safety)

**💡 핵심 지식 포인트:**
*   **프로세스 vs 스레드 메모리 공간 구조 비교:**
    *   *프로세스 격리:* 프로세스는 OS의 가상 메모리 시스템에 의해 서로 철저히 격리되어 있어, 한 프로세스가 비정상 종료(Crash)되어도 다른 프로세스에 직접적 영향을 주지 않습니다. 두 프로세스 간 통신은 비용이 큰 IPC(파이프, 소켓, 공유 메모리)를 써야 합니다.
    *   *스레드 공유:* 스레드들은 힙 메모리와 전역 변수를 공유하므로 데이터 전달이 매우 빠르고 통신 비용이 거의 없습니다. 그러나 **한 스레드가 힙 메모리를 오염시키거나 예외로 크래시되면 프로세스 전체가 다운**되는 치명적 취약점이 존재합니다.
*   **멀티스레딩 환경의 핵심 난제 3가지:**
    1.  **경쟁 상태 (Race Condition) & 임계 영역 (Critical Section):**
        *   두 개 이상의 스레드가 공유 자원(메모리)에 동시에 접근하여 쓰기 작업을 수행할 때, 실행 순서나 타이밍에 따라 결과가 달라지는 비결정적 버그.
        *   공유 자원을 조작하는 코드 영역인 임계 영역은 반드시 상호 배제(Mutual Exclusion)가 보장되어야 함.
    2.  **동기화 기법 (Synchronization Primitives):**
        *   **뮤텍스 (Mutex):** 락(Lock)을 획득한 단 1개의 스레드만 임계 영역에 진입 가능(소유권 개념 존재).
        *   **세마포어 (Semaphore):** 동시에 진입 가능한 스레드의 개수($N$)를 제어하는 카운팅 신호 메커니즘.
    3.  **교착 상태 (Deadlock)와 4대 필수 조건 (Coffman Conditions):**
        *   *정의:* 두 개 이상의 스레드나 프로세스가 서로가 점유한 자원의 락이 풀리기만을 무한히 기다리며 시스템 전체의 진행이 완전히 멈춰버리는 현상.
        *   *4대 성립 조건 (4가지가 **동시에 모두 충족**되어야만 데드락 발생):*
            1.  **상호 배제 (Mutual Exclusion):**
                *   자원은 한 번에 오직 **단 하나의 프로세스/스레드만 사용**할 수 있어야 함 (배타적 자원).
                *   다른 스레드가 이미 사용 중인 자원을 요청하면, 그 자원이 해제될 때까지 반드시 대기해야 함.
            2.  **점유 대기 (Hold and Wait):**
                *   최소한 하나의 자원을 이미 **점유(Hold)한 상태에서**, 다른 스레드에 의해 할당된 새로운 자원을 추가로 획득하기 위해 **대기(Wait)**하고 있는 스레드가 존재해야 함.
                *   즉, 자신이 쥔 락을 내려놓지 않은 채 다른 락을 요구하는 상태.
            3.  **비선점 (No Preemption):**
                *   다른 프로세스/스레드가 이미 점유하고 있는 자원을 **강제로 빼앗을 수 없음**.
                *   자원을 점유한 스레드가 작업을 정상적으로 마치고 스스로 자발적으로 락을 해제(Release)할 때까지 외부에서 회수할 수 없음.
            4.  **순환 대기 (Circular Wait):**
                *   자원을 기다리는 스레드들의 집합 $\{T_0, T_1, \dots, T_n\}$에서, $T_0$은 $T_1$의 자원을, $T_1$은 $T_2$의 자원을, $\dots$, $T_n$은 다시 $T_0$의 자원을 대기하며 **원형 고리(Cycle) 형태의 대기 사슬**을 형성해야 함.
        *   *예방 원리:* 위 4가지 조건 중 **단 하나라도 성립하지 않도록 차단**하면 교착 상태는 결코 발생하지 않음 (실무에서는 주로 자원 번호에 따라 오름차순으로만 락을 얻게 하는 **Lock Ordering**을 통해 '순환 대기'를 원천 파괴함).
*   **💡 실무 적용 팁:**
    *   락을 획득할 때는 반드시 모든 스레드가 **일관된 순서로 락을 획득(Lock Ordering)**하도록 설계해야 순환 대기를 원천 차단할 수 있습니다. 또한 락 프리(Lock-free) 알고리즘이나 원자적 연산(Atomic Operation / CAS)을 활용하면 락으로 인한 성능 저하를 방지할 수 있습니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "컨텍스트 스위칭(Context Switching) 시 프로세스 간 전환이 스레드 간 전환보다 훨씬 무겁고 느린 하드웨어적 이유는 무엇인가요?"**
    *   👉 **답변 포인트:** 동일 프로세스 내 스레드 전환은 CPU 레지스터 세트와 스택 포인터만 교체하면 되며 CPU 캐시가 유지됩니다. 반면 프로세스 전환은 메모리 관리 장치(MMU)의 **페이지 테이블 베이스 레지스터(CR3 등)를 교체**해야 합니다. 이로 인해 가상 주소를 물리 주소로 초고속 변환해 주던 하드웨어 캐시인 **TLB(Translation Lookaside Buffer)가 완전히 플러시(무효화)**되어, 전환 직후 극심한 메모리 지연(TLB 미스 및 CPU 캐시 미스)이 발생하기 때문입니다.
*   **Q2. "파이썬(CPython)은 멀티스레드를 지원하지만 왜 멀티코어 CPU 병렬 연산에 멀티스레딩을 권장하지 않나요?"**
    *   👉 **답변 포인트:** CPython 인터프리터 내부에 **GIL(Global Interpreter Lock)**이 존재하여, 코어가 여러 개여도 특정 순간에 단 하나의 스레드만 파이썬 바이트코드를 실행할 수 있기 때문입니다. CPU 연산이 주를 이루는 작업에서는 멀티스레드를 쓰면 스레드 간 락 경합과 컨텍스트 스위칭 비용만 추가되어 싱글스레드보다 오히려 느려집니다. 따라서 파이썬에서는 `multiprocessing` 모듈을 써서 아예 별도의 독립 프로세스를 띄워야 코어별 병렬 처리가 가능합니다.

**📚 필수 핵심 용어 해설:**
*   **교착 상태 4대 조건 (Coffman Conditions):** 교착 상태가 발생하기 위해 반드시 동시에 충족되어야 하는 4가지 조건(상호 배제, 점유 대기, 비선점, 순환 대기).
*   **임계 영역 (Critical Section):** 둘 이상의 스레드가 공유 자원에 동시에 접근하면 데이터 무결성이 훼손될 수 있어, 한 번에 오직 하나의 스레드만 진입하도록 보호해야 하는 코드 구간.
*   **TLB (Translation Lookaside Buffer):** CPU가 가상 메모리 주소를 실제 물리 메모리 주소로 빠르게 변환하기 위해 최근 변환 정보를 캐싱해 두는 하드웨어 고속 캐시.

### 8. 버전 관리 시스템(예: Git)을 사용하는 이유와, 브랜치 전략에 대해 설명해 주세요.
> **질문:** 버전 관리 시스템(예: Git)을 사용하는 이유와, 브랜치 전략에 대해 설명해 주세요.

**🎯 면접관 필수 체크 키워드:**
*   [ ] **버전 관리 시스템(VCS)의 본질적 사용 목적:** 변경 이력 추적, 시점 복구(Rollback), 코드 충돌 해결, 책임 소재 파악(`git blame`), 비동기 협업
*   [ ] **분산 버전 관리(DVCS) vs 중앙 집중식(CVCS):** 모든 개발자가 로컬에 완전한 저장소 복제본을 보유(오프라인 작업 및 독립적 브랜칭 가능)
*   [ ] **Git의 핵심 데이터 모델:** 스냅샷(Snapshot) 기반 불변 객체 모델(Blob, Tree, Commit)과 비순환 방향 그래프(DAG)
*   [ ] **대표적 브랜치 전략 3종 비교:**
    *   **Git-flow:** 5가지 브랜치(main, develop, feature, release, hotfix) 기반의 엄격하고 안정적인 전통적 전략
    *   **GitHub-flow:** `main` 브랜치와 짧은 수명의 피처 브랜치(PR 기반) 중심의 단순하고 빠른 지속적 배포(CD) 전략
    *   **Trunk-based Development:** 브랜치를 최소화하고 메인 트렁크에 매일 빈번하게 통합하는 최신 DevOps/CI 전략
*   [ ] **실무 충돌 및 머지 전략:** Merge Commit vs Squash and Merge vs Rebase and Merge

**💡 핵심 지식 포인트:**
*   **Git 브랜치 전략 3대 모델 심층 비교:**
    1.  **Git-flow (정기 릴리즈 주기가 있는 대규모 프로젝트에 적합):**
        *   `main`: 실제 프로덕션에 배포된 버전만 관리하는 영구 브랜치.
        *   `develop`: 다음 배포를 위해 개발된 기능들이 통합되는 영구 브랜치.
        *   `feature`: 새로운 기능 단위 개발 브랜치(`develop`에서 분기 $\to$ `develop`으로 머지).
        *   `release`: 배포 전 최종 버그 픽스 및 QA 검증 브랜치(`develop`에서 분기 $\to$ `main`, `develop` 양쪽 머지).
        *   `hotfix`: 배포된 프로덕션 긴급 장애 대응 브랜치(`main`에서 분기 $\to$ `main`, `develop` 양쪽 머지).
        *   *단점:* 브랜치 구조가 복잡하여 머지 충돌이 빈번하고 지속적 배포(CD) 파이프라인의 민첩성을 저해.
    2.  **GitHub-flow (SaaS 웹 서비스 및 CI/CD 지속적 배포에 적합):**
        *   `main` 브랜치는 항상 언제든 프로덕션에 배포 가능한 상태(Always Deployable)를 유지.
        *   새로운 작업 시 명확한 이름의 피처 브랜치를 `main`에서 분기.
        *   수시로 커밋하고 푸시한 뒤, 작업이 완료되면 **Pull Request (PR)**를 열어 코드 리뷰와 자동화 테스트를 거침.
        *   PR이 승인되면 `main`에 머지하고 즉시 프로덕션에 자동 배포.
    3.  **Trunk-based Development (최신 고성과 DevOps 팀 표준):**
        *   개발자들이 브랜치를 길게 유지하지 않고, 매일 최소 1~2회 메인 브랜치(Trunk)에 직접 또는 초단기 PR을 통해 코드를 머지.
        *   미완성 기능이 프로덕션에 노출되지 않도록 **기능 플래그(Feature Flags / Toggles)** 기법을 필수로 동반.
*   **💡 실무 머지 전략 팁:**
    *   `Squash and Merge`는 피처 브랜치의 자잘한 커밋들(WIP, 오타 수정 등)을 깔끔하게 단 1개의 커밋으로 압축하여 `main`에 머지하므로, 메인 브랜치의 히스토리를 군더더기 없이 일목요연하게 관리할 수 있어 실무에서 가장 선호됩니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "`git merge`와 `git rebase`의 차이점은 무엇이며, 어떤 상황에서 각각을 선택해야 하나요?"**
    *   👉 **답변 포인트:** `git merge`는 두 브랜치의 분기점과 최신 커밋을 합치는 새로운 '머지 커밋'을 생성하여 실제 브랜치 히스토리를 정직하게 보존합니다. 반면 `git rebase`는 내 작업 브랜치의 베이스 커밋을 대상 브랜치의 최신 커밋 뒤로 재배치하여 **커밋 히스토리를 단일 선형(Linear) 형태로 깔끔하게 재작성**합니다. 단, 이미 원격 저장소에 푸시되어 다른 동료와 공유 중인 공용 브랜치에서는 히스토리 불일치 사고를 방지하기 위해 절대 rebase를 수행해서는 안 됩니다(Golden Rule of Rebase).
*   **Q2. "Git에서 실수로 중요한 커밋을 날려버렸거나(`git reset --hard`), 삭제된 브랜치를 복구하고 싶을 때 사용하는 명령어와 원리는 무엇인가요?"**
    *   👉 **답변 포인트:** **`git reflog`** 명령어를 사용합니다. Git은 브랜치의 참조(HEAD)가 변경된 모든 이력을 일정 기간(기본 30~90일) 동안 reflog에 독립적으로 기록해 둡니다. 아무리 브랜치가 지워지거나 hard reset을 했더라도 해당 커밋 객체는 가비지 컬렉션(GC)되기 전까지 저장소에 온전히 남아있으므로, `git reflog`로 해당 시점의 커밋 해시를 찾아 `git checkout` 또는 `git reset`으로 완벽히 복구할 수 있습니다.

**📚 필수 핵심 용어 해설:**
*   **기능 플래그 (Feature Flag / Toggle):** 코드를 프로덕션에 이미 배포해 두었더라도, 설정 플래그(True/False)를 통해 런타임에 특정 기능의 활성화 여부를 코드 재배포 없이 동적으로 제어하는 배포 기법.
*   **Reflog (Reference Log):** 로컬 저장소에서 HEAD 포인터가 가리켰던 모든 과거 위치의 기록을 순차적으로 보관하는 안전망 로그.

### 9. 단위 테스트(Unit Test)와 통합 테스트(Integration Test)의 차이점은 무엇이며, 각각 언제 사용하나요?
> **질문:** 단위 테스트(Unit Test)와 통합 테스트(Integration Test)의 차이점은 무엇이며, 각각 언제 사용하나요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **테스트 피라미드 (Test Pyramid):** 단위 테스트(기저, 다수/빠름/저비용) $\to$ 통합 테스트(중간) $\to$ E2E/시스템 테스트(상단, 소수/느림/고비용)의 이상적 비율
*   [ ] **단위 테스트 (Unit Test):**
    *   범위: 함수, 메서드, 클래스 등 외부 의존성과 완전히 격리된 가장 작은 논리적 단위
    *   도구: Mock, Stub, Spy 등 테스트 더블(Test Double)을 활용한 격리
    *   장점: 수 밀리초 단위의 극도로 빠른 실행 속도, 정확한 실패 지점 포착, 리팩토링 안정망
*   [ ] **통합 테스트 (Integration Test):**
    *   범위: 여러 컴포넌트가 유기적으로 결합된 상호작용, 실제 DB 쿼리, 외부 네트워크 연동 검증
    *   목적: 단위 테스트가 보장하지 못하는 스키마 불일치, 직렬화/역직렬화 오류, 트랜잭션 롤백, 연동 결함 포착
*   [ ] **테스트 더블(Test Double) 5가지 분류:** Dummy, Fake, Stub, Spy, Mock의 역할 차이
*   [ ] **TDD (테스트 주도 개발)의 사이클:** Red $\to$ Green $\to$ Refactor

**💡 핵심 지식 포인트:**
*   **단위 테스트 vs 통합 테스트 특성 상세 비교:**
    | 구분 | 단위 테스트 (Unit Test) | 통합 테스트 (Integration Test) |
    | :--- | :--- | :--- |
    | **테스트 대상** | 단일 클래스, 순수 함수, 비즈니스 도메인 로직 | 컴포넌트 간 상호작용, DB 영속성, 외부 API 통신 |
    | **격리 수준** | 외부 환경(DB, 네트워크)을 100% 모킹하여 완벽 격리 | 실제 인메모리 DB(H2 등)나 도커 컨테이너(Testcontainers) 연동 |
    | **실행 속도** | 수천 개가 수 초(ms 단위) 내에 즉각 실행 | I/O와 커넥션 비용으로 인해 수 분(sec 단위) 소요 |
    | **주요 목적** | 복잡한 계산 알고리즘, 경계값(Edge case) 조건문 검증 | 레이어 간 인터페이스 정합성, 트랜잭션 격리수준, SQL 문법 검증 |
    | **피드백 주기** | 로컬에서 코드 저장 시마다 수시 실행 (TDD 가능) | PR 생성 시 또는 CI 파이프라인에서 주기적 실행 |
*   **테스트 더블(Test Double) 핵심 3종 구별:**
    1.  **Stub:** 호출에 대해 미리 준비된 고정된 데이터(하드코딩된 값)를 반환하는 객체 (상태 기반 검증).
    2.  **Mock:** 어떤 메서드가 몇 번, 어떤 파라미터로 호출되었는지 호출 행위 자체를 기록하고 검증하는 객체 (행위 기반 검증).
    3.  **Fake:** 실제 동작하는 구현체를 가지되 상용 환경에는 부적합한 단순화된 객체 (예: 인메모리 딕셔너리 기반 DB).
*   **💡 실무 적용 팁:**
    *   단위 테스트만 통과했다고 소프트웨어가 정상 작동한다고 믿는 것은 위험합니다(단위 테스트 100% 패스해도 실제 DB 컬럼 매핑 오류로 500 에러 발생 가능). 따라서 비즈니스 로직은 빠른 단위 테스트로 촘촘히 보호하고, DB 쿼리와 핵심 API 엔드포인트는 통합 테스트로 교차 검증하는 포트폴리오를 구성해야 합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "테스트 코드 작성 시 '모킹(Mocking)을 과도하게 남용했을 때' 발생하는 역효과는 무엇인가요?"**
    *   👉 **답변 포인트:** 실제 구현체의 세부 동작 방식을 테스트 코드가 지나치게 자세히 모킹하면, 리팩토링으로 내부 구현을 조금만 바꿔도 비즈니스 결과가 올바른데도 테스트가 깨져버리는 **'취약한 테스트(Brittle Test)'**가 됩니다. 이는 테스트 코드가 내부 구현 세부사항(Implementation Details)에 강하게 결합되었기 때문이며, 모킹은 DB나 외부 결제 API 같은 순수 외부 경계에 한정하고 도메인 내부 객체 간 협력은 실제 객체를 쓰는 것이 바람직합니다.
*   **Q2. "통합 테스트 환경에서 테스트 데이터 격리(Test Isolation)를 보장하기 위해 주로 어떤 기법들을 사용하나요?"**
    *   👉 **답변 포인트:** 테스트가 끝날 때마다 DB 트랜잭션을 롤백하는 `@Transactional` 롤백 전략을 사용하거나, 테스트 실행 직전 DB 테이블의 데이터를 초기화(Truncate)하는 스크립트를 실행합니다. 최근에는 환경 일관성을 위해 도커 기반으로 독립된 경량 DB 인스턴스를 동적으로 띄워주는 **Testcontainers** 라이브러리가 표준으로 사용됩니다.

**📚 필수 핵심 용어 해설:**
*   **테스트 더블 (Test Double):** 영화 촬영에서 위험한 스턴트 대역을 쓰듯, 테스트 시 실제 복잡한 의존성 객체(DB, 메일 서버 등)를 대신하여 사용되는 모든 가짜 객체의 총칭.
*   **Testcontainers:** 통합 테스트 실행 시 실제 환경과 동일한 Docker 컨테이너(MySQL, Redis, Kafka 등)를 런타임에 코드로 자동 생성하고 테스트 종료 후 파기해 주는 테스트 프레임워크.

### 10. 가비지 컬렉션(Garbage Collection)이 무엇이며, 메모리 관리 측면에서 어떤 장단점이 있나요?
> **질문:** 가비지 컬렉션(Garbage Collection)이 무엇이며, 메모리 관리 측면에서 어떤 장단점이 있나요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **가비지 컬렉션(GC)의 정의:** 런타임 환경(JVM, V8, CLR, Python 등)이 동적으로 할당된 힙(Heap) 메모리를 감시하여, 더 이상 참조되지 않는 객체를 자동으로 감지하고 회수하는 메모리 관리 메커니즘
*   [ ] **도달 가능성(Reachability)과 Root Set:** 스택의 지역 변수, static 변수 등 루트 객체로부터 유효한 참조 사슬이 이어져 있는가 여부 판별
*   [ ] **장점:** 수동 메모리 관리(`malloc`/`free`)의 인간 실수 제거, 메모리 누수 완화, 댕글링 포인터(Dangling Pointer) 및 이중 해제(Double Free) 방지
*   [ ] **단점:** **Stop-The-World (STW)** 현상에 의한 일시적 시스템 멈춤 및 지연(Latency), 메모리 해제 시점의 비결정성(Non-deterministic), GC 실행 자체를 위한 CPU/메모리 부가 오버헤드
*   [ ] **주요 GC 알고리즘:** 참조 계수(Reference Counting), 마크 앤 스윕(Mark-and-Sweep), 세대별 GC(Generational GC)

**💡 핵심 지식 포인트:**
*   **수동 메모리 관리 vs 가비지 컬렉션의 핵심 대비:**
    *   C/C++ 같은 수동 관리 언어는 개발자가 메모리를 직접 해제해야 하므로 성능이 극도로 높지만, 실수로 해제하지 않으면 **메모리 누수(Memory Leak)**가 발생하고, 이미 해제된 메모리를 다시 가리키는 **댕글링 포인터(Dangling Pointer)**나 같은 메모리를 두 번 해제하는 **이중 해제(Double Free)**로 인한 보안 취약점과 크래시가 빈번함.
    *   GC 기반 언어(Java, Go, Python, JS)는 가상머신이 백그라운드에서 메모리를 전담 관리하므로 개발 생산성과 메모리 안전성을 획기적으로 향상시킴.
*   **세대별 가비지 컬렉션 (Generational GC)의 동작 원리:**
    *   대부분의 GC는 **약한 세대 가설(Weak Generational Hypothesis)**에 기반합니다:
        1.  대부분의 객체는 생성된 직후 매우 짧은 시간 내에 쓸모없어진다(Unreachable).
        2.  오래 살아남은 객체에서 젊은 객체로의 참조는 매우 드물다.
    *   따라서 힙 영역을 **Young 영역(Eden + Survivor)**과 **Old 영역**으로 물리적으로 분리합니다.
        *   새로 생성된 객체는 Eden에 들어가며, 금방 죽으므로 좁은 Young 영역만 빠르게 훑어 수집하는 **Minor GC**를 빈번하게 실행(STW 시간이 수 ms로 극히 짧음).
        *   Minor GC에서 살아남은 객체는 Age Bit를 올리며 Survivor를 거쳐 일정 기준을 넘으면 Old 영역으로 승격(Promotion).
        *   Old 영역이 가득 차면 실행되는 **Major GC (Full GC)**는 힙 전체를 스캔하므로 긴 STW를 유발.
*   **💡 실무 적용 팁:**
    *   GC가 있다고 해서 메모리 누수가 100% 방지되는 것은 아닙니다. 전역 정적(static) 컬렉션에 객체를 넣어두고 제거하지 않거나, 리스너를 해제하지 않는 경우 여전히 Root Set과 연결되어 있어 GC가 영원히 회수하지 못하는 **논리적 메모리 누수(Memory Leak)**가 발생합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "파이썬(Python)은 주로 참조 계수(Reference Counting) 방식을 사용하는데, 이 방식의 치명적인 한계와 파이썬은 이를 어떻게 해결하나요?"**
    *   👉 **답변 포인트:** 참조 계수는 객체를 가리키는 포인터 수를 세다가 0이 되는 즉시 해제하므로 직관적이지만, **순환 참조(Circular Reference)** 문제가 발생합니다. 예컨대 객체 A가 B를 가리키고 B가 다시 A를 가리키는 상태에서 외부 참조가 끊어지면, 둘 다 영원히 카운트가 1로 남아 메모리에서 회수되지 않습니다. 파이썬은 이를 해결하기 위해 참조 계수 외에 백그라운드에서 객체 그래프를 탐색하여 순환 참조를 감지하고 깨뜨리는 **세대별 순환 가비지 컬렉터(Cyclic Garbage Collector)**를 보조 엔진으로 함께 구동합니다.
*   **Q2. "대규모 트래픽을 처리하는 Java 서버 애플리케이션에서 GC로 인한 STW(Stop-The-World) 시간을 줄이기 위해 최근 실무에서 널리 채택하는 모던 GC 알고리즘은 무엇인가요?"**
    *   👉 **답변 포인트:** 과거의 Parallel GC나 CMS GC의 한계를 넘어, 대용량 힙 메모리를 수천 개의 작은 리전(Region) 단위로 분할하여 점진적으로 가비지를 수거하는 **G1 GC(Garbage-First GC)**가 Java 9 이후 기본값으로 정착했습니다. 나아가 수백 GB 이상의 초대용량 힙에서도 STW 멈춤 시간을 최대 수 밀리초 이하로 극단적으로 억제하는 저지연 GC인 **ZGC**나 **Shenandoah GC**가 활발히 도입되고 있습니다.

**📚 필수 핵심 용어 해설:**
*   **Stop-The-World (STW):** 가비지 컬렉션을 수행하기 위해 애플리케이션의 모든 비즈니스 스레드 실행을 일시적으로 완전히 중단시키는 가상머신의 동작 상태.
*   **댕글링 포인터 (Dangling Pointer):** 이미 메모리 상에서 해제(Free)되어 유효하지 않은 힙 주소를 여전히 가리키고 있는 포인터로, 접근 시 프로그램 충돌이나 심각한 보안 취약점 유발.
