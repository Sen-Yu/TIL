## 2. 질문별 세부 분석 및 피드백

### Q1. HTTP와 HTTPS의 차이 및 로그인/결제 시 필수 이유
*   **답변 내용:** HTTP는 평문(Plaintext)으로 통신하고, HTTPS는 보안 프로토콜인 SSL/TLS를 사용해 암호화된 텍스트를 주고받음. 로그인/결제 시 개인정보 탈취(피싱, 패킷 훼손 등)를 방지하기 위해 필수적임.
*   **👍 잘한 점:** 평문과 암호화의 대비, SSL/TLS 프로토콜 명시, 민감 정보 보호 필요성을 군더더기 없이 두괄식으로 정확히 설명했습니다.
*   **💡 개선 팁:** '피싱'이라는 단어보다는 **'스니핑(Sniffing/네트워크 도청)'** 또는 **'중간자 공격(MITM)'**이라는 표준 보안 용어를 사용하시면 더욱 전문성이 돋보입니다.

---

### Q2. HTTPS의 암호화 외의 추가 보안 효과 (인증, 무결성)
*   **답변 내용:** 데이터 암호화 외에 '인증'과 '무결성' 효과가 있음. 가짜 피싱 서버로 가로채는 것을 방지(인증서)하고, 중간에 데이터가 위변조되었을 때 수학적으로 검증하여 변조된 데이터를 버리고 재요청함.
*   **👍 잘한 점:** 정보보안의 핵심인 **인증(Authentication)**과 **무결성(Integrity)** 두 축을 명확히 제시하고, 데이터 변조 시 버리고 재요청한다는 구체적인 동작 흐름까지 완벽히 짚었습니다.
*   **💡 개선 팁:** "공인된 인증기관(CA)의 디지털 서명을 통한 신원 보증"과 "해시 기반 무결성 검증(MAC)"이라는 표현을 한 줄 덧붙이면 100점짜리 답변입니다.

---

### Q3. FastAPI 데이터 불일치 처리 및 Pydantic의 편리함
*   **답변 내용:** 기본적으로 422 Unprocessable Entity 에러가 발생함. Pydantic이 없다면 수동으로 파서를 구현하거나 if문/예외 처리를 직접 짜야 하지만, Pydantic을 쓰면 타입 힌트를 기반으로 데이터 수신/생성 시 자동 검증해 주어 개발자 생산성이 극대화됨.
*   **👍 잘한 점:** 422 상태 코드를 정확히 언급했고, 과거의 수동 if문 검증(보일러플레이트)과 Pydantic의 자동 검증을 훌륭하게 대조했습니다.
*   **💡 개선 팁:** Pydantic의 **자동 타입 캐스팅(문자열 "10" -> 정수 10)**과 **Swagger UI 문서 자동 연동** 장점까지 한 줄 곁들이면 더욱 완벽합니다.

### Q5. API/모델 오류 시 사용자에게 알려주는 전략
*   **답변 내용:** AI 모델 생성 실패 시 무작정 재시도하며 사용자를 무한 대기시키지 않고 상태를 전달해야 함. 특히 에러를 즉시 띄우기보다 성능이 조금 떨어지더라도 **폴백(Fallback) 데이터**를 대신 보여줌으로써 사용성과 안정감을 유지해야 함.
*   **👍 잘한 점:** **오늘 면접 최고의 답변 중 하나입니다!** 단순히 에러 메시지를 띄우는 차원을 넘어, **"폴백(Fallback)을 통한 서비스 흐름 유지(Graceful Degradation)"**를 언급한 점은 사용자 경험(UX)을 깊이 고민해 본 개발자만이 할 수 있는 특급 답변이었습니다.
*   **💡 개선 팁:** 사용자 화면에서 프롬프트가 날아가지 않도록 입력값을 보존하고, `[다시 시도]` 버튼을 함께 제공한다는 실무 UX 디테일을 추가하면 완벽합니다.

---

### Q6. 기본 예외 처리 vs 직접 정의한 커스텀 예외의 차이
*   **답변 내용:** 기본 예외 처리는 보편적이고 두루뭉술함. 서비스가 커지면 '재고 부족', 'DB 데이터 없음' 같은 특별한 비즈니스 상황이 생기는데, 커스텀 예외를 정의하면 개발자도 원인을 명확히 알고 사용자에게도 정확한 상황을 전달할 수 있음.
*   **👍 잘한 점:** **'재고 부족'**이라는 구체적이고 현실적인 비즈니스 도메인 예시를 들어 커스텀 예외의 필요성을 매우 설득력 있게 풀어냈습니다.
*   **💡 개선 팁:** FastAPI의 `@app.exception_handler` 전역 핸들러와 연결하여 "앱 전체의 에러 응답 포맷을 일관된 JSON 규격으로 통일할 수 있다"는 아키텍처적 이점을 덧붙이면 좋습니다.

### Q7. AI 모델 API 동시 요청 폭주와 동기 방식의 문제점
*   **답변 내용:** AI 모델 쪽 스레드 풀이 하나씩 차면서 포화되고, 결국 최신 요청이 드랍(유실)됨. 통신 메시지 버퍼도 차서 패킷이 버려지고 전체 시스템 마비로 이어짐.
*   **👍 잘한 점:** 단일 요청 지연이 전체 스레드 풀 고갈과 버퍼 오버플로우, 요청 유실로 번지는 연쇄 장애 메커니즘을 시스템 관점에서 훌륭하게 설명했습니다.
*   **💡 개선 팁:** 문제점 지적에 이어 *"이를 해결하기 위해 웹 서버는 접수증(202 Accepted)만 주고 실제 연산은 Celery/Redis 같은 비동기 큐 워커로 오프로딩해야 합니다"*라고 솔루션까지 이어가면 시니어급 인상을 줍니다.

---

### Q8. FastAPI async/await가 모든 상황에서 더 빠른가?
*   **답변 내용:** 단발성 요청은 속도 차이가 없음. 비동기는 동시성에 대한 처리임. 텐서 변환 같은 CPU 연산이 많은 작업에서 비동기를 쓰면 파이썬의 싱글 스레드 특성상 스레드가 묶여 블로킹이 발생하고, 결국 스레드 풀이 넘치게 됨.
*   **👍 잘한 점:** **이번 모의면접의 하이라이트 답변입니다.**
    * "비동기는 단일 속도(Latency)가 아니라 동시성(Throughput) 기술이다"
    * "텐서 변환 같은 CPU 연산이 발생하면 파이썬 싱글 스레드가 블로킹된다"
    스스로 "너무 깊게 들어갔나"라고 걱정하셨지만, **절대 아닙니다.** 면접관이 이 질문을 던지는 이유가 바로 이 블로킹 현상을 알고 있는지 떠보기 위함인데, 정답의 핵심을 정확히 타격하셨습니다.
*   **💡 개선 팁:** 스스로 위축되지 마시고 당당하게 말씀하셔도 좋습니다! "따라서 CPU 바운드 작업은 `async def`가 아닌 일반 `def`(FastAPI 스레드풀 위임)로 작성하거나 별도 프로세스로 격리해야 합니다"로 마무리하시면 100점입니다.

---

### Q9. AI API에서 비동기가 유용한 경우 vs 안 유용한 경우
*   **답변 내용:** 
    * 유용한 경우: 외부 LLM API(OpenAI 등)를 호출하는 경우. 간접 통신(I/O 바운드)이므로 비동기의 이점을 살려 스케일링이 잘 됨.
    * 안 유용한 경우: 온프레미스/로컬 서버에서 직접 GPU/모델을 운영할 때. 연산 단위가 커서 락이 걸리고 블로킹 상태가 발생할 가능성이 높음.
*   **👍 잘한 점:** 8번에서 언급한 이론을 AI 서빙 실무(외부 API 연동 vs 온프레미스 모델 구동)에 정확하게 1:1로 매핑하여 훌륭하게 대조했습니다.

### Q10. AI 모델 API 서비스 전체 설계 (입력~출력)
*   **답변 내용:** 1~9번의 내용이 종합된 문제라 순간적으로 정리가 어려워 충분히 답변하지 못함.
*   **💡 개선 및 준비 가이드:**
    이런 종합 아키텍처 질문은 완벽한 코드를 말하라는 것이 아니라 **전체 파이프라인의 4단계 목차**를 깔끔하게 제시하면 됩니다:
    1. **입력 (Input):** Pydantic으로 데이터 타입, 길이, 이미지 규격 엄격 검증 및 프롬프트 인젝션 차단
    2. **추론 (Processing):** FastAPI 메인 서버에서 직접 연산하지 않고, Celery/Redis 작업 큐나 Triton 서버로 추론 오프로딩
    3. **오류 (Error):** 도메인 커스텀 예외와 Fallback 메커니즘을 두어 모델 실패 시에도 대체 데이터 반환
    4. **응답 (Output):** Pydantic Response Model로 규격화하고, LLM 답변은 SSE 스트리밍으로 실시간 전달
