# 3주차 웹 & FastAPI 모의면접 핵심 정리 & 면접관 체크리스트

이 문서는 **면접자**에게는 고득점 답변 구성을 위한 핵심 지침서이며, **면접관**에게는 답변 검증용 필수 키워드 체크리스트 및 심층 꼬리 질문 가이드로 활용됩니다.

### 1. HTTP와 HTTPS의 차이, 민감한 서비스에서 HTTPS 필수 이유
> **질문:** HTTP로 통신하는 것과 HTTPS로 통신하는 것은 실제로 어떤 차이가 있나요? 그리고 로그인이나 결제 같은 서비스에서는 왜 HTTPS를 사용해야 할까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **평문 vs 암호화:** HTTP는 평문(Plaintext) 전송, HTTPS는 SSL/TLS 기반 암호화 전송
*   [ ] **보안 위협 방어:** 스니핑(Sniffing/네트워크 도청) 및 중간자 공격(MITM) 차단
*   [ ] **하이브리드 암호화 메커니즘:** 비대칭키(키 교환) + 대칭키(실제 대용량 데이터 암호화) 결합
*   [ ] **로그인/결제 보호:** 비밀번호, 카드번호, 세션 토큰 탈취 방지

**💡 핵심 지식 포인트:**
*   **차이점:** HTTP는 데이터를 아무런 암호화 없이 있는 그대로(평문) 전송하여 패킷 감청에 취약함. HTTPS는 SSL/TLS 프로토콜을 사용해 통신 구간 전체를 암호화함.
*   **필수 이유:** 로그인 비밀번호나 결제 카드 정보가 평문으로 흐르면 중간에 패킷을 가로챘을 때 즉시 유출되므로, 전송 구간 암호화가 법적/기술적으로 필수임.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "왜 처음부터 끝까지 안전한 비대칭키(공개키/개인키)로 암호화하지 않고, 대칭키를 섞어 쓰는 하이브리드 방식을 쓸까요?"**
    *   👉 **답변 포인트:** 비대칭키 암호화는 복잡한 수학 연산(소수인수분해 등)이 필요하여 CPU 부하가 매우 크고 속도가 느립니다. 따라서 안전하게 대칭키를 교환할 때만 비대칭키를 사용하고, 이후 대용량 데이터 통신은 연산이 훨씬 빠른 대칭키(AES 등)를 사용하는 것이 성능상 최적이기 때문입니다.

**📚 필수 핵심 용어 해설:**
*   **평문 (Plaintext):** 암호화되지 않은 원본 텍스트 데이터.
*   **스니핑 (Sniffing):** 네트워크 상에 오고 가는 패킷을 몰래 훔쳐보는 도청 행위.
*   **TLS 핸드셰이크:** 통신 시작 시 서로 암호화 알고리즘을 조율하고 비밀키를 안전하게 교환하는 과정.

### 2. HTTPS의 암호화 외의 추가 보안 효과 (무결성, 인증)
> **질문:** HTTPS를 사용하면 데이터가 암호화된다고 하는데, 단순히 데이터를 암호화하는 것 외에 어떤 보안 효과가 있나요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **인증 (Authentication):** 내가 접속한 사이트가 진짜 맞는지 공인 인증기관(CA)의 인증서로 증명
*   [ ] **무결성 (Integrity):** 전송 도중 해커에 의해 데이터가 위조/변조/훼손되지 않았음을 보장
*   [ ] **피싱/위장 서버 방지:** 악의적 프록시나 피싱 도메인 접속 차단
*   [ ] **변조 감지 메커니즘:** 해시 및 메시지 인증 코드(MAC/HMAC)를 통한 변조 감지

**💡 핵심 지식 포인트:**
*   단순히 데이터를 숨기는 기밀성(Confidentiality) 외에, **신원을 보증하는 '인증'**과 **변조를 막는 '무결성'**이 HTTPS의 3대 축임.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "클라이언트(브라우저)는 서버가 보낸 인증서가 진짜인지 어떻게 검증하고 신뢰하나요?"**
    *   👉 **답변 포인트:** 브라우저와 OS에는 전 세계적으로 신뢰받는 루트 인증기관(Root CA)들의 공개키가 이미 하드코딩되어 있습니다. 서버가 보낸 인증서는 이 루트 CA가 디지털 서명한 체인(Chain of Trust)을 형성하고 있어, 클라이언트가 이를 역추적하여 위조 여부를 수학적으로 검증합니다.

**📚 필수 핵심 용어 해설:**
*   **무결성 (Integrity):** 데이터가 중간에 악의적으로 변경되거나 누락되지 않고 온전함을 보장하는 특성.
*   **인증서 (SSL Certificate):** 신뢰할 수 있는 공인 기관(CA)이 서버의 신원을 보증해 주는 디지털 신분증.

### 3. FastAPI의 데이터 검증 처리 및 Pydantic의 장점 (서버/클라이언트 관점)
> **질문:** FastAPI에서 사용자가 보내는 데이터가 우리가 기대한 형식과 다르다면 어떻게 처리할 수 있을까요? Pydantic을 사용하면 어떤 점이 편리한가요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **기본 422 에러 (Unprocessable Entity):** 규격 불일치 시 자동 에러 반환
*   [ ] **실무 RequestValidationError 커스텀:** `@app.exception_handler`로 사용자 친화적 에러 포맷 가공
*   [ ] **서버 측 장점:** 선언적 검증(if문 보일러플레이트 제거), 자동 타입 캐스팅, `dict` 대신 객체 주입(타입 안전성), `response_model` 민감 정보 필터링
*   [ ] **클라이언트 측 장점:** 상세한 필드별 에러 피드백(`loc`, `msg`), 일관된 JSON 스키마 수신, Swagger UI 자동 연동

**💡 핵심 지식 포인트:**
*   과거 Flask 등에서 수동으로 일일이 if문으로 타입을 검사하던 고통을 없애고, Pydantic 모델에 선언만 하면 파싱, 검증, 에러 응답, 문서화까지 프레임워크가 자동화해 줌.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "Pydantic v1과 v2의 가장 큰 기술적 차이점이 무엇인가요?"**
    *   👉 **답변 포인트:** 핵심 검증 및 직렬화 엔진이 순수 파이썬에서 Rust 언어 기반의 `pydantic-core`로 완전히 재작성되어, 데이터 파싱 및 검증 속도가 최대 5배~17배까지 비약적으로 향상되었습니다.

**📚 필수 핵심 용어 해설:**
*   **선언적 프로그래밍 (Declarative):** 절차적 if문을 나열하지 않고 데이터의 형태를 모델에 선언하는 방식.
*   **타입 캐스팅 (Type Coercion):** 문자열 `"10"`이 들어와도 선언된 `int` 타입으로 안전하게 자동 변환하는 기능.
*   **RequestValidationError:** Pydantic 검증 실패 시 발생하는 핵심 예외 클래스.

### 4. AI 모델 API 서비스 시 입력 사전 검증의 중요성
> **질문:** AI 모델을 API로 서비스한다고 했을 때, 사용자가 잘못된 형식이나 비정상적인 값을 보내는 것을 왜 미리 검증하는 것이 중요할까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **비싼 GPU 연산 리소스/비용 낭비 방지 (Early Rejection):** 가벼운 웹 서버 레벨에서 선제 차단
*   [ ] **GPU OOM (Out Of Memory) 방지:** 수만 자의 과도한 텍스트나 비정상 해상도 이미지 차단
*   [ ] **프롬프트 인젝션 (Prompt Injection) 등 보안 방어:** 악의적 시스템 조작 차단
*   [ ] **GIGO (Garbage In, Garbage Out) 차단:** 쓰레기 값으로 인한 기괴한 예측 결과 방지

**💡 핵심 지식 포인트:**
*   AI 모델 추론은 CPU/GPU 비용이 극도로 비쌉니다. 유효하지 않은 요청이 모델까지 흘러 들어가면 자원 낭비와 OOM이 발생하므로, 애플리케이션 앞단(FastAPI)에서 철저히 문지기 역할을 수행해야 합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "텍스트 길이를 검증할 때 단순 글자 수(Characters) 검증과 토큰 수(Tokens) 검증의 차이는 무엇인가요?"**
    *   👉 **답변 포인트:** LLM 모델의 컨텍스트 한계는 글자 수가 아니라 토큰 수로 결정됩니다. 한글이나 특수문자는 글자 수는 적어도 토큰 수가 폭증할 수 있으므로, 엄격한 서빙 환경에서는 Tiktoken 같은 라이브러리로 토큰 수를 사전 검증하여 모델에 전달해야 합니다.

**📚 필수 핵심 용어 해설:**
*   **GIGO (Garbage In, Garbage Out):** 쓰레기 값이 들어가면 쓰레기 결과가 나온다는 컴퓨터 공학 격언.
*   **프롬프트 인젝션:** 사용자가 악의적 프롬프트를 주입하여 시스템 지침을 무력화하려는 공격.

### 5. API 오류(서버/모델 오류) 발생 시 사용자 응답 전략
> **질문:** API를 운영하다 보면 잘못된 요청뿐만 아니라 서버 오류나 AI 모델의 예측 실패도 발생할 수 있습니다. 이런 상황에서 사용자에게는 어떤 식으로 오류를 알려주는 것이 좋을까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **사용자 눈높이 언어:** 500 에러, Timeout, OOM 등 기술 용어 노출 배제
*   [ ] **구체적 수정 가이드 vs 대기 안내:** 사용자 입력 오류는 해결법 제시, 서버 과부하는 대기 시간 안내
*   [ ] **행동 유도 (Actionable UX):** `[다시 시도]` 버튼 제공 및 작성 중이던 프롬프트 입력값 보존
*   [ ] **폴백 (Fallback / Graceful Degradation):** 실패 시 기본 추천 목록이나 캐시 데이터를 대신 노출
*   [ ] **간단한 참조 코드 (#E-9102) 제공:** 고객센터(CS) 문의 시 활용

**💡 핵심 지식 포인트:**
*   에러 화면을 마주하는 일반 사용자(End User)에게 기술적 내부 에러를 노출하지 않고, 친절한 설명과 다음 행동(다시 시도/입력값 보존), 그리고 폴백 데이터를 제공하여 서비스 이탈을 방지함.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "AI 모델이 과부하(Overload) 상태일 때 사용자의 `[다시 시도]` 버튼 연타로 서버가 더 심하게 마비되는 현상을 어떻게 막을 수 있을까요?"**
    *   👉 **답변 포인트:** 클라이언트 단에서 지수 백오프(Exponential Backoff)와 Jitter(랜덤 지연)를 적용하고, 재시도 버튼에 쿨다운(Debounce/Throttle) 타이머를 적용하여 트래픽 스파이크를 분산시킵니다.

**📚 필수 핵심 용어 해설:**
*   **폴백 (Fallback):** 장애 시 서비스 중단을 막기 위해 기본값이나 대체 데이터를 제공하는 안전장치.
*   **우아한 기능 저하 (Graceful Degradation):** 일부 기능이 실패해도 전체 서비스가 중단되지 않고 제한된 기능으로 지속되는 설계.

### 6. 기본 예외 처리 vs 커스텀 예외(Custom Exception)의 차이
> **질문:** FastAPI에서 예외가 발생했을 때 기본적인 예외 처리만 사용하는 것과 직접 예외를 정의해서 처리하는 것에는 어떤 차이가 있을까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **비즈니스 도메인 맥락 표현:** "재고 부족", "모델 로딩 중", "크레딧 부족" 등 명확한 예외 정의
*   [ ] **전역 예외 처리기 (`@app.exception_handler`) 연동:** 앱 전체 에러를 한곳에서 가로채기
*   [ ] **일관된 에러 JSON 규격 통일:** 프론트엔드와의 통신 규격 표준화
*   [ ] **코드 파편화 방지:** 라우터마다 중복 작성되던 HTTPException 제거 및 유지보수성 향상

**💡 핵심 지식 포인트:**
*   기본 예외 처리는 일반적인 HTTP 에러를 다루기엔 충분하지만 비즈니스 맥락을 담기 어렵습니다. 커스텀 예외를 정의하고 전역 핸들러와 묶으면 앱 전체에서 통일된 JSON 포맷으로 일괄 대응할 수 있습니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "FastAPI에서 Python 표준 `Exception`을 전역 핸들러로 무작정 다 잡아버리면 어떤 부작용이 생기나요?"**
    *   👉 **답변 포인트:** 내부 ASGI 취소 신호나 정상 라이프사이클 이벤트까지 삼켜버릴 수 있으며, 개발자의 단순 오타나 문법 버그의 스택 트레이스를 숨겨 디버깅이 극도로 어려워집니다. 세부적인 커스텀 예외를 먼저 잡고 범용 예외는 최상단 로깅용으로만 제한해야 합니다.

**📚 필수 핵심 용어 해설:**
*   **도메인 예외 (Domain Exception):** 서비스 비즈니스 규칙 위반에 맞춰 구체적으로 이름을 지은 예외 클래스.
*   **전역 예외 처리기 (Global Exception Handler):** 앱 어디서든 예외가 발생하면 가로채어 규격화된 응답을 만드는 처리소.

### 7. AI 모델 API의 높은 동시 요청과 동기(Sync) 처리의 문제점 및 해결 방안
> **질문:** AI 모델을 호출하는 API를 만들었는데 요청이 동시에 아주 많이 들어온다면, 일반적인 동기 방식으로 처리할 때 어떤 문제가 생길 수 있을까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **스레드 블로킹 (Blocking):** 1개 요청의 AI 추론(3~5초) 동안 워커 스레드가 꼼짝 못 하고 묶임
*   [ ] **스레드 풀 고갈 (Thread Pool Exhaustion):** 동시 요청이 워커 수를 넘어서면 큐에서 무한 대기
*   [ ] **연쇄적 504 Timeout & 헬스체크 마비:** 단순 조회 요청까지 서버 전체가 먹통
*   [ ] **실무 해결책 1 (오프로딩):** Celery, Redis, RabbitMQ 비동기 작업 큐로 오프로딩 (`202 Accepted`)
*   [ ] **실무 해결책 2 (서빙 엔진):** Triton, vLLM을 활용한 동적 배치(Dynamic Batching)로 GPU 처리량 극대화

**💡 핵심 지식 포인트:**
*   동기 방식으로 처리하면 워커 스레드가 무거운 AI 연산에 묶여 서버 전체가 마비됩니다. 이를 해결하기 위해 웹 서버는 접수증만 즉시 반환하고 실제 연산은 비동기 작업 큐 워커로 넘기거나 전용 추론 엔진(동적 배치)을 분리해야 합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "동적 배치(Dynamic Batching)의 원리와 트레이드오프는 무엇인가요?"**
    *   👉 **답변 포인트:** 개별 요청들을 몇 밀리초(ms) 동안 큐에 모아 하나의 큰 배치 텐서로 묶어 GPU에 전달함으로써 GPU 처리량(Throughput)을 극대화합니다. 트레이드오프는 배치를 모으는 짧은 시간(Queue delay)만큼 개별 요청의 지연 시간(Latency)이 아주 미세하게 증가할 수 있습니다.

**📚 필수 핵심 용어 해설:**
*   **스레드 풀 고갈:** 모든 일꾼이 무거운 작업에 투입되어 신규 요청을 받을 일꾼이 0명이 된 상태.
*   **동적 배치 (Dynamic Batching):** 개별 요청을 짧은 시간 모아 한 번의 GPU 연산으로 묶어 처리하는 기술.
*   **작업 오프로딩:** 무거운 짐을 가벼운 웹 서버가 들지 않고 전용 백그라운드 워커로 떠넘기는 설계.

### 8. FastAPI 비동기(async/await)의 한계와 적합/부적합 상황
> **질문:** FastAPI의 async와 await를 사용하면 여러 요청을 효율적으로 처리할 수 있다고 하는데, 이것이 모든 상황에서 더 빠르다는 의미일까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **속도의 오해:** 단일 작업 속도(Latency) 단축이 아니라 대기 시간을 활용한 동시 처리량(Throughput) 극대화
*   [ ] **I/O 바운드 적합:** DB 쿼리, Redis, 외부 서드파티 API, S3 업로드 등 대기 시간 활용
*   [ ] **CPU 바운드 부적합:** 텐서 변환, 행렬 연산 등에서 파이썬 싱글 스레드 이벤트 루프가 락(블로킹)에 걸림
*   [ ] **FastAPI 일반 `def`의 스레드 풀 위임:** 블로킹 연산은 `async def`가 아닌 일반 `def`(`run_in_threadpool`)로 작성

**💡 핵심 지식 포인트:**
*   비동기가 무조건 빠른 것이 아니며, I/O 대기에서는 수천 개의 동시 처리를 가능하게 하지만, CPU 연산에 잘못 쓰면 싱글 스레드 이벤트 루프가 멈춰버려 서버 전체가 마비됩니다. 블로킹 코드는 일반 `def`로 격리해야 합니다.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "`async def` 안에서 `time.sleep(5)`를 호출하면 왜 치명적이고, `asyncio.sleep(5)`는 왜 안전한가요?"**
    *   👉 **답변 포인트:** `time.sleep()`은 파이썬 스레드 자체를 멈춰버리는 동기 블로킹 함수이므로 이벤트 루프가 5초간 꽁꽁 얼어붙습니다. 반면 `asyncio.sleep()`은 이벤트 루프에 타이머만 등록하고 `await`로 즉시 제어권을 넘기므로 다른 사용자 요청이 정상 처리됩니다.

**📚 필수 핵심 용어 해설:**
*   **이벤트 루프 블로킹:** 싱글 스레드 지휘자가 무거운 연산에 잡혀 멈춰 서버 전체가 마비되는 현상.
*   **스레드 풀 위임 (Threadpool Delegation):** FastAPI가 일반 `def` 함수를 만났을 때 메인 루프를 막지 않도록 내부 워커 스레드로 작업을 격리 던져주는 기능.

### 9. AI 모델 API에서 비동기가 유용한 경우 vs 독이 되는 경우
> **질문:** AI 모델 추론 API에서 비동기 처리가 특히 유용한 상황과 오히려 큰 도움이 되지 않는 상황을 각각 예로 들어 설명해 주실 수 있을까요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **유용한 상황 (I/O 바운드):** 외부 LLM API(OpenAI 등) 연동, S3 이미지 비동기 다운로드 및 DB 로깅
*   [ ] **실시간 토큰 스트리밍 (SSE):** `StreamingResponse` + `async for ... yield`를 결합한 체감 대기 지연 단축
*   [ ] **독이 되는 상황 (CPU/GPU 바운드):** 로컬 메모리에 PyTorch/ONNX 모델을 올리고 직접 추론하는 상황
*   [ ] **GPU 블로킹의 진실 (면접 핵심 방어):** 전처리(NumPy 텐서 변환)는 CPU가 수행하며, GPU 연산 대기(CUDA 동기화) 시 파이썬 메인 스레드가 블로킹됨

**💡 핵심 지식 포인트:**
*   외부 API 호출과 스트리밍(SSE)에는 비동기가 최적이지만, 로컬 PyTorch 직접 추론 시에는 파이썬 CPU 전처리와 CUDA 동기화로 인해 이벤트 루프가 멈추므로 전용 추론 워커로 분리해야 함.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "CUDA 비동기 스트림 연산과 파이썬 asyncio의 비동기는 같은 것인가요?"**
    *   👉 **답변 포인트:** 다릅니다. CUDA 비동기는 CPU와 GPU 하드웨어 칩셋 간의 비동기 파이프라인이고, asyncio는 파이썬 싱글 스레드 안에서의 소프트웨어적 태스크 스케줄링입니다. 파이썬이 GPU 연산 결과를 꺼내 쓰려면 동기화(`cudaStreamSynchronize`)가 필요하므로 asyncio 이벤트 루프가 멈추게 됩니다.

**📚 필수 핵심 용어 해설:**
*   **스트리밍 응답 (StreamingResponse):** 전체 답변 완성을 기다리지 않고 생성되는 토큰 조각을 실시간 전송하는 기법.
*   **CUDA 동기화 블로킹:** GPU 연산 결과를 파이썬이 읽기 위해 대기할 때 CPU 스레드가 멈추는 현상.

### 10. AI 모델 API 서비스의 전체 설계 고려사항
> **질문:** 사용자가 AI 모델에 요청을 보내고 결과를 받는 서비스를 직접 만든다고 한다면, 입력 검증부터 모델 추론, 오류 처리, 응답 반환까지 어떤 부분들을 고려해서 설계하시겠어요?

**🎯 면접관 필수 체크 키워드:**
*   [ ] **1단계 입력 (Input):** Pydantic을 통한 타입/길이/해상도 사전 검증 및 프롬프트 인젝션 차단
*   [ ] **2단계 추론 (Processing):** 웹 서버와 무거운 추론 엔진 분리 (Celery/Redis 작업 큐 또는 Triton 오프로딩)
*   [ ] **3단계 오류 (Error):** 도메인 커스텀 예외와 Fallback(폴백 데이터)을 통한 서비스 흐름 유지
*   [ ] **4단계 응답 (Output):** Pydantic Response Model 규격화 및 SSE(Server-Sent Events) 실시간 토큰 스트리밍

**💡 핵심 지식 포인트:**
*   입력(Pydantic 방화벽) $\rightarrow$ 추론(비동기 큐/전문 엔진 오프로딩) $\rightarrow$ 에러(커스텀 예외 및 폴백) $\rightarrow$ 응답(Response Model 및 SSE 스트리밍)의 4단계 파이프라인으로 구성함.

**🔍 심층 꼬리 질문 & 대응 가이드 (면접관용):**
*   **Q1. "비동기 작업 큐로 추론을 오프로딩했을 때, 최종 사용자는 결과를 어떤 방식으로 수신하는 것이 가장 좋을까요?"**
    *   👉 **답변 포인트:** 작업이 수 초 내외인 일반 대화형 AI라면 웹소켓이나 SSE 연결을 유지해 실시간 Push로 전달하고, 이미지/동영상 생성처럼 수 분 이상 걸리는 대규모 작업이라면 작업 접수 시 `task_id`를 주고 상태 조회용 Polling 엔드포인트나 Webhook 알림을 제공하는 것이 표준 아키텍처입니다.

**📚 필수 핵심 용어 해설:**
*   **비동기 작업 큐 (Task Queue):** 작업을 접수받아 백그라운드 워커에게 분배하는 아키텍처.
*   **SSE (Server-Sent Events):** 서버가 클라이언트에게 단방향으로 실시간 데이터를 지속 전송하는 HTTP 표준 기술.
