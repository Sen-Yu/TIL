# LangChain

## 텍스트 분할

### Text Splitter
- **Document를 작은 Document들로 분할**하는 LangChain 컴포넌트의 표준 인터페이스
- 사용이유: 작게 청크로 분할해서 내용 정밀도와 토큰 한도 비용 감소를 위해서(Document가 클수록 정밀도와 토큰 비용 증가) 
- chunck: 분할된 작은 Document
  - 원본 Document의 page_content를 나누고, 각 chunk에 원본 metadata를 함께 전달
- 분할기준

| 분할기 | 기준 |
|---|---|
| RecursiveCharacterTextSplitter | 문단, 줄바꿈, 공백 같은 구분자를 우선순위대로 사용해 분할합니다. |
| CharacterTextSplitter | 지정한 하나의 구분자를 기준으로 분할합니다. |
| TokenTextSplitter | 토큰 수를 기준으로 분할합니다. |
| MarkdownHeaderTextSplitter | 마크다운 헤더 구조를 기준으로 분할합니다. |
| HTMLHeaderTextSplitter | HTML 헤더 구조를 기준으로 분할합니다. |


- 파이프라인
~~~

    Text,PDF,JSON,Web HTML
              │
              ▼
  ┌─────────────────────────┐              
  │     Document Loader     │
  └───────────┬─────────────┘
              │                         Document(
       Document(Original)                 page_content="긴 문서 전체 내용...",                    
              │                           metadata={"source": "manual.pdf", "page": 3}
              ▼                         )
  ┌─────────────────────────┐
  │       Text Splitter     │
  └───────────┬─────────────┘
              │                        [Document(page_content="첫 번째 chunk...", metadata={"source": "manual.pdf", "page": 3}),
  [Document1, ..., Document N]                                            ...                                                ,
              │                         Document(page_content="N 번째 chunk...", metadata={"source": "manual.pdf", "page": 3}),]                                     
              ▼

~~~


#### TokenTextSpliiter
- Document를 토큰 수를 기준으로 분할하는 텍스트 분할기
- 사용이유: 글자 수와 토큰 수는 비례하지 않음(한국어처럼 한 글자가 여러 토큰이 되는 언어에서 발생)
  예) 같은 양의 토큰으로 영어 프롬프트는 안전한지만, 한국어 프롬프트는 토큰 한도 초과 호출 발생
- tiktoken
  - OpenAI 모델에서 사용하는 토큰 계산 방식에 맞춰 텍스트를 토큰으로 나누는 라이브러리
 
## 임베딩과 벡터 저장소

### Embeddings
- 자연어를 벡터로 변환(word2vec)하는 표준 인터페이스
- 언어 모델의 임베딩과 차이점
  - 트랜스포머 모델의 일부(토큰임베딩 + 위치 인코딩)
- 사용이유
  - 모델변경마다 임베딩 방식을 변경할 필요없음
- 설치
~~~
!pip install -q langchain langchain-google-genai
~~~ 
- 코드
~~~
from langchain_google_genai import GoogleGenerativeAIEmbeddings

## 1.embeddings 구현체
embeddings = GoogleGenerativeAIEmbeddings(
    model="models/gemini-embedding-001",      ## Google Gemini의 임베딩 모델 gemini-embedding-001
    google_api_key="YOUR_API_KEY",
)
## 2.Dcoument List
texts = [
    "어댑터즈는 스타트업코드에서 제공하는 개발 책 서빙 서비스입니다.",
    "어댑터즈는 개발자 교육 콘텐츠를 제공합니다.",
    "오늘 날씨가 정말 맑습니다.",
]
## 3.벡터 변환
vectors = embeddings.embed_documents(texts)    ## embed_documents() 여러 문서를 한번에 벡터로 변환하는 메서드

## 4.단일 질의 벡터 변환
query = "어댑터즈는 어떤 서비스인가요?"
query_vector = embeddings.embed_query(query)

## 5.유사도 계산으로 의미 거리 확인
import numpy as np
## 유사도 계산
def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
# 단일 질의와 각 벡터 유사도 계산
sim_0 = cosine(query_vector, vectors[0])  # 어댑터즈 = 개발 책 서빙 서비스
sim_1 = cosine(query_vector, vectors[1])  # 어댑터즈 = 개발자 교육 콘텐츠
sim_2 = cosine(query_vector, vectors[2])  # 오늘 날씨가 맑습니다

print(f"질의 vs 문서0 (어댑터즈 소개):  {sim_0:.4f}")
print(f"질의 vs 문서1 (어댑터즈 콘텐츠): {sim_1:.4f}")
print(f"질의 vs 문서2 (날씨):           {sim_2:.4f}")
~~~   

### VectorStore Interface
- 모든 벡터 데이터베이스 구현체가 따르는 LangChain의 표준 인터페이스(문서 벡터 저장소)
- 파이프라인 위치: Embeddings과 Retriever 사이를 연결하는 컴포넌트
- 사용이유: 벡터 DB 종류에 관계없이 동일한 코드로 인덱싱, 검색, Retriever 변환을 수행하여 DB 교체 비용을 최소화하기 위해서

~~~
# 아래의 두 VDB중 선택해서 사용
from <package> import SomeVectorStore
## 1.Croma: 로컬 환경에서 벡터 저장·검색을 구현
from langchain_chroma import Chroma
## 2.FAISS: 대량 벡터 검색을 로컬 메모리에서 신속 처리
from langchain_community.vectorstores import FAISS

## 인덱싱
vectorstore = SomeVectorStore.from_documents(docs, embeddings)

## 검색
results = vectorstore.similarity_search(query, k=3)
results_with_scores = vectorstore.similarity_search_with_score(query, k=3)

## Retriever 변환
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})
~~~

#### Croma
- 별도의 데이터베이스 서버 없이 파이썬 환경에서 사용할 수 있는 임베디드 방식의 VDB
- 저장 정보: 임베딩벡터(Document 벡터), 문서내용(원본 Document), 메타데이터(출처,주제,파일명,카테고리,etc)
- 저장방식: 실행 중 메모리 보관, 로컬 디렉터리에 데이터 보존
- 사용이유
  - RAG 구조 실습
  - 자체 서버형 VDB 사용전 작은 데이터셋 검색 품질 검증

#### FAISS
- Meta가 공개한 메모리 기반 고속 유사도 검색 VDB 라이브러리
- 메모리 기반이여서 프로세스가 종료되면 인덱스 사라짐(휘발성) -> 인덱스 재사용을 위해서는 별도로 로컬에 저장 및 로드 필요
- 저장 정보: 임베딩벡터(Document 벡터), 문서내용(원본 Document), 메타데이터(출처,주제,파일명,카테고리,etc)
- 사용이유
  - 대량 벡터 검색을 빠르게 처리하기 위해 사용
