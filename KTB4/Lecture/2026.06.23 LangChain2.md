# LangChain

## 텍스트 분할

### Text Splitter
- **Document를 작은 Document들로 분할**하는 LangChain 컴포넌트의 표준 인터페이스
- 사용이유: 작게 청크로 분할해서 내용 정밀도와 토큰 한도 비용 감소를 위해서(Document가 클수록 정밀도와 토큰 비용 증가) 
- chunck: 분할된 작은 Document
  - 원본 Document의 page_content를 나누고, 각 chunk에 원본 metadata를 함께 전달
- 분할기준

| 분할기 | 기준 |
|---|---|
| RecursiveCharacterTextSplitter | 문단, 줄바꿈, 공백 같은 구분자를 우선순위대로 사용해 분할합니다. |
| CharacterTextSplitter | 지정한 하나의 구분자를 기준으로 분할합니다. |
| TokenTextSplitter | 토큰 수를 기준으로 분할합니다. |
| MarkdownHeaderTextSplitter | 마크다운 헤더 구조를 기준으로 분할합니다. |
| HTMLHeaderTextSplitter | HTML 헤더 구조를 기준으로 분할합니다. |


- 파이프라인
~~~

    Text,PDF,JSON,Web HTML
              │
              ▼
  ┌─────────────────────────┐              
  │     Document Loader     │
  └───────────┬─────────────┘
              │                         Document(
       Document(Original)                 page_content="긴 문서 전체 내용...",                    
              │                           metadata={"source": "manual.pdf", "page": 3}
              ▼                         )
  ┌─────────────────────────┐
  │       Text Splitter     │
  └───────────┬─────────────┘
              │                        [Document(page_content="첫 번째 chunk...", metadata={"source": "manual.pdf", "page": 3}),
  [Document1, ..., Document N]                                            ...                                                ,
              │                         Document(page_content="N 번째 chunk...", metadata={"source": "manual.pdf", "page": 3}),]                                     
              ▼

~~~


#### TokenTextSpliiter
- Document를 토큰 수를 기준으로 분할하는 텍스트 분할기
- 사용이유: 글자 수와 토큰 수는 비례하지 않음(한국어처럼 한 글자가 여러 토큰이 되는 언어에서 발생)
  예) 같은 양의 토큰으로 영어 프롬프트는 안전한지만, 한국어 프롬프트는 토큰 한도 초과 호출 발생
- tiktoken
  - OpenAI 모델에서 사용하는 토큰 계산 방식에 맞춰 텍스트를 토큰으로 나누는 라이브러리
 
## 임베딩과 벡터 저장소

### Embeddings
- 자연어를 벡터로 변환(word2vec)하는 표준 인터페이스
- 언어 모델의 임베딩과 차이점
  - 트랜스포머 모델의 일부(토큰임베딩 + 위치 인코딩)
- 사용이유
  - 모델변경마다 임베딩 방식을 변경할 필요없음
- 설치
~~~
!pip install -q langchain langchain-google-genai
~~~ 
- 코드
~~~
from langchain_google_genai import GoogleGenerativeAIEmbeddings

## 1.embeddings 구현체
embeddings = GoogleGenerativeAIEmbeddings(
    model="models/gemini-embedding-001",      ## Google Gemini의 임베딩 모델 gemini-embedding-001
    google_api_key="YOUR_API_KEY",
)
## 2.Dcoument List
texts = [
    "어댑터즈는 스타트업코드에서 제공하는 개발 책 서빙 서비스입니다.",
    "어댑터즈는 개발자 교육 콘텐츠를 제공합니다.",
    "오늘 날씨가 정말 맑습니다.",
]
## 3.벡터 변환
vectors = embeddings.embed_documents(texts)    ## embed_documents() 여러 문서를 한번에 벡터로 변환하는 메서드

## 4.단일 질의 벡터 변환
query = "어댑터즈는 어떤 서비스인가요?"
query_vector = embeddings.embed_query(query)

## 5.유사도 계산으로 의미 거리 확인
import numpy as np
## 유사도 계산
def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))
# 단일 질의와 각 벡터 유사도 계산
sim_0 = cosine(query_vector, vectors[0])  # 어댑터즈 = 개발 책 서빙 서비스
sim_1 = cosine(query_vector, vectors[1])  # 어댑터즈 = 개발자 교육 콘텐츠
sim_2 = cosine(query_vector, vectors[2])  # 오늘 날씨가 맑습니다

print(f"질의 vs 문서0 (어댑터즈 소개):  {sim_0:.4f}")
print(f"질의 vs 문서1 (어댑터즈 콘텐츠): {sim_1:.4f}")
print(f"질의 vs 문서2 (날씨):           {sim_2:.4f}")
~~~   

### VectorStore Interface
- 모든 벡터 데이터베이스 구현체가 따르는 LangChain의 표준 인터페이스(문서 벡터 저장소)
- 파이프라인 위치: Embeddings과 Retriever 사이를 연결하는 컴포넌트
- 사용이유: 벡터 DB 종류에 관계없이 동일한 코드로 인덱싱, 검색, Retriever 변환을 수행하여 DB 교체 비용을 최소화하기 위해서

~~~
# 아래의 두 VDB중 선택해서 사용
from <package> import SomeVectorStore
## 1.Croma: 로컬 환경에서 벡터 저장·검색을 구현
from langchain_chroma import Chroma
## 2.FAISS: 대량 벡터 검색을 로컬 메모리에서 신속 처리
from langchain_community.vectorstores import FAISS

## 인덱싱
vectorstore = SomeVectorStore.from_documents(docs, embeddings)

## 검색
results = vectorstore.similarity_search(query, k=3)
results_with_scores = vectorstore.similarity_search_with_score(query, k=3)

## Retriever 변환
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})
~~~

#### Croma
- 별도의 데이터베이스 서버 없이 파이썬 환경에서 사용할 수 있는 임베디드 방식의 VDB
- 저장 정보: 임베딩벡터(Document 벡터), 문서내용(원본 Document), 메타데이터(출처,주제,파일명,카테고리,etc)
- 저장방식: 실행 중 메모리 보관, 로컬 디렉터리에 데이터 보존
- 사용이유
  - RAG 구조 실습
  - 자체 서버형 VDB 사용전 작은 데이터셋 검색 품질 검증

#### FAISS
- Meta가 공개한 메모리 기반 고속 유사도 검색 VDB 라이브러리
- 메모리 기반이여서 프로세스가 종료되면 인덱스 사라짐(휘발성) -> 인덱스 재사용을 위해서는 별도로 로컬에 저장 및 로드 필요
- 저장 정보: 임베딩벡터(Document 벡터), 문서내용(원본 Document), 메타데이터(출처,주제,파일명,카테고리,etc)
- 사용이유
  - 대량 벡터 검색을 빠르게 처리하기 위해 사용

| 방식 | 특징 | 적합한 상황 |
|---|---|---|
| FAISS | 메모리 기반 고속 벡터 검색 라이브러리입니다. HNSW, IVF, PQ 같은 다양한 인덱스 구조를 사용할 수 있어 검색 성능을 세밀하게 조정할 수 있습니다. 다만 영구 저장은 save_local()과 load_local()로 직접 처리해야 하고, metadata 필터링이나 분산 처리 같은 운영 기능은 제공하지 않아 저장소 운영 기능이 제한적입니다. | 자체 서버나 로컬 환경에서 대량 벡터를 빠르게 검색해야 할 때 적합합니다. |
| Chroma | 파이썬 환경에서 바로 사용할 수 있는 임베디드형 벡터 데이터베이스입니다. 인메모리 모드와 영구 저장 모드를 쉽게 전환할 수 있고, metadata 필터링도 비교적 편하게 사용할 수 있습니다. 다만 대규모 트래픽이나 다중 사용자 동시 접근 같은 프로덕션급 운영에는 한계가 있습니다. | 로컬 개발, 실습, 소규모 RAG 프로토타입에 적합합니다. |
| Pinecone, Weaviate, Qdrant 등 클라우드 관리형 벡터 DB | 벡터 저장, 인덱스 관리, 확장, 운영 기능을 서비스 형태로 제공합니다. 영구 저장, 분산 처리, metadata 필터링, 권한 관리 같은 운영 기능이 강하지만, 사용량 기반 비용과 네트워크 지연이 발생할 수 있습니다. | 실제 서비스 운영, 대규모 트래픽, 여러 사용자 데이터 관리가 필요한 상황에 적합합니다. |
| Milvus | 오픈소스 분산 벡터 DB로 직접 호스팅하거나 클라우드(Zilliz Cloud)로도 사용할 수 있습니다. 대규모 벡터의 분산 저장과 인덱스 확장에 강하지만, 직접 운영할 경우 인프라 관리 부담이 큽니다. | 대규모 벡터를 자체 인프라에서 분산 운영해야 하는 상황에 적합합니다. |
| pgvector | PostgreSQL 확장으로, 기존 관계형 DB 테이블에 벡터 컬럼을 추가해 사용합니다. 별도 벡터 DB 도입 없이 SQL과 벡터 검색을 함께 쓸 수 있지만, 대규모·고차원 벡터에서는 전용 벡터 DB보다 성능이 떨어질 수 있습니다. | 이미 PostgreSQL을 사용 중이고 별도 인프라 추가 없이 벡터 검색을 도입하려는 상황에 적합합니다. |



## 검색 추상화와 고급 Retrieval

### Retriever
- 사용이유
  - 검색결과가 Documnet 리스트로 통일해서 다음 파이프라인 단계 안정화, VectorStore와 독립적이기에 검색전략이 바뀌어도 수정범위가 좁음
  - VectorStore.similarity_search()
    - VectorStore 객체가 제공하는 일반 검색 메서드
    - 직접호출해도 관련 문서 얻는게 불가능  
#### BaseRetriever
- LangChain의 모든 Retriever의 공통 인터페이스

- 핵심 메소드
  
| 메서드 | 입력 / 출력 | 역할 |
|---|---|---|
| invoke(query) | 입력: str<br>출력: List[Document] | 질의 한 건을 받아 관련 문서 리스트로 반환, 최신 LangChain에서 기본적으로 사용 |
| ainvoke(query) | 입력: str<br>출력: List[Document] | invoke()의 비동기 버전, async/await 환경에서 질의 한 건을 비동기로 처리할 때 사용 |
| batch(queries) | 입력: List[str]<br>출력: List[List[Document]] | 여러 질의를 한 번에 처리, 각 질의마다 관련 문서 리스트가 반환 |
| abatch(queries) | 입력: List[str]<br>출력: List[List[Document]] | batch()의 비동기 버전, 여러 질의를 비동기로 동시에 처리할 때 사용 |

- 코드(형태)
~~~
## Retriever 객체 생성
retriever = vectorstore.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 3},
)

## 단독 호출(invoke)
docs = retriever.invoke("질의 문자열")

## 리스트를 하나의 문자열로 합침
def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

## LCEL 체인 연결
chain = (
    ### context: 검색결과들을 하나의 문자열로 함침 , question: RunnablePassthrough()가 질의를 그대로 통과
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | model
    | parser
)
~~~

#### Ensemble Retriever
- 여러 Retriever의 Document 검색 결과를 RRF 방식으로 순위를 통합하여 하나의 리스트로 반환하는 LangChain 합성 Retriever(Hybrid와 유사)
  - RRF(Reciprocal Rank Fusion)

$$
\text{RRF Score}(d) = \sum_i \frac{w_i}{c + \text{rank}_i(d)}
$$

| **기호** | **의미** | 예시 |
| --- | --- | --- |
| $d$ | 점수를 계산할 문서입니다. | `문서 A`가 최종 검색 결과에 포함될 후보라면, RRF는 `문서 A`의 점수를 계산합니다. |
| $\text{rank}_i(d)$ | 문서 $d$가 $i$번째 Retriever에서 받은 순위입니다.
1등이면 1입니다. | `문서 A`가 BM25 Retriever에서는 1위, VectorStore Retriever에서는 3위로 나왔다면 각각 `rank_1(A)=1`, `rank_2(A)=3`입니다. |
| $w_i$ | $i$번째 Retriever에 부여한 가중치입니다. | BM25와 VectorStore를 같은 비중으로 보면 `[0.5, 0.5]`를 사용하고, 의미 검색을 더 중요하게 보면 `[0.3, 0.7]`처럼 설정할 수 있습니다. |
| $c$ | 순위 차이의 영향을 완화하는 상수입니다.
LangChain의 기본값은 60입니다. | $c$가 크면 1위와 5위의 점수 차이가 완만해지고, $c$가 작으면 상위 순위 문서가 더 강하게 반영됩니다. |

공식이 복잡해 보여도 원리는 단순합니다.
