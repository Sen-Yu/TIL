# RAG
- 질문 시점에 필요한 정보를 찾아와서 기존 정보와 함께 사용하는 방식
  - 외부 데이터에서 **관련 문서 검색**, LLM 프롬프트 **입력에 함께 넣고** **답변을 생성**하는 시스템패턴
- 파이프라인 단계
  - 인덱싱(Indexing) 단계: Document Loading -> Chunking -> Embedding -> Vector Store
  - 질의(Query) 단계: Retrieval -> Augmentation -> Generation

## Embedding (임베딩)
- 청크를 임베딩하여 의미 벡터로 변환
### Tokenization (토큰화) 
- 텍스트를 일정한 단위(토큰)로 분리하는 과정
- 주요 방식(입력: "Startupcode is a company.")
  - 워드(Word): 공백,구두점 기준으로 단어 분리 ["Startupcode", "is", "a", "company."]
  - 서브워드(SubWord): 빈도 기반 부분 문자열 ["Start", "up", "code", "is", "a", "company", "."]
  - 캐릭터(Character): 글자 단위 ["S", "t", "a", "r", "t", "u", "p", ...]
   
- 종류
  
| 항목 | **GPT 계열** | **BERT 계열** |
|---|---|---|
| **아키텍처** | Decoder-only (자기회귀) | Encoder-only (양방향) |
| **학습 방식** | 다음 토큰 예측 (Causal LM) | 마스크 언어 모델 (MLM) + NSP |
| **Tokenizer 방식** | BPE (Byte Pair Encoding) | WordPiece |
| **대표 모델** | GPT-2, GPT-3, GPT-4, GPT-4o, LLaMA, Mistral, Claude | BERT, DistilBERT, ALBERT, RoBERTa, DeBERTa |
| 개발사 | OpenAI, Meta, Mistral AI 등 | Google, HuggingFace 커뮤니티 |
| **주요 용도 (RAG)** | **최종 답변 생성 (Generator)** | **문서 검색 및 임베딩 (Retriever)** |

### Text Embedding (텍스트 임베딩)
- **텍스트 토큰**을 **고정 길이 의미 벡터**로 **변환**하는 과정
  - 예) "어댑터즈는 스타트업코드에서 제공하는 개발 책 서빙 서비스입니다."  ->	[0.023, -0.041, 0.118, ..., 0.067] (384차원)
- Sentence Transformers
  - 문장 전체를 하나의 벡터로 표현     

### Dense Vector (밀집 벡터) / Sparse Vector (희소 벡터)

| 비교 항목 | **Dense Vector (밀집 벡터)** | **Sparse Vector (희소 벡터)** |
|---|---|---|
| **정의** | 모든 차원에 **실수값이 채워진 저차원 벡터** | **대부분의 값이 0**이고 일부만 값이 있는 **고차원 벡터** |
| **차원 수** | 128 ~ 4096차원 (압축된 의미 공간) | 어휘 크기만큼 (수만 ~ 수십만 차원) |
| **값의 분포** | 모든 차원에 값 존재 (조밀함) | 대부분 0, 단어 등장 위치만 비0 (희소함) |
| **표현 방식** | 학습된 임베딩 모델이 의미를 압축 | 단어의 등장 여부·빈도를 직접 기록 |
| **생성 방법** | 신경망 기반 임베딩 모델 (BERT 등) | 통계 기반 알고리즘 (TF-IDF, BM25) |
| **대표 알고리즘/모델** | `bge-m3`, `e5-large`, `OpenAI Embeddings` | TF-IDF, BM25, One-Hot Encoding |
| **검색 방식** | 코사인 유사도, 내적 기반 ANN 검색 | 역색인(Inverted Index) 기반 정확 매칭 |
| **의미 유사도 표현** | ✅ 가능 (동의어·문맥 이해) | ❌ 불가능 (정확히 같은 단어만 매칭) |
| **정확한 키워드 매칭** | ❌ 취약 (고유명사·코드·약어) | ✅ 강함 |
| **해석 가능성** | ❌ 낮음 (각 차원이 무엇을 의미하는지 불명확) | ✅ 높음 (각 차원이 특정 단어에 대응) |
| **저장 공간** | 차원 수만큼 고정 (압축적) | 비0 값만 저장 시 효율적 (역색인 구조 활용) |
| **계산 비용** | 벡터 내적 연산, GPU 활용 시 빠름 | 역색인 조회로 매우 빠름 |
| **학습 필요 여부** | 필요 (사전학습 임베딩 모델) | 불필요 (통계 계산만으로 생성) |
| **언어 의존성** | 모델 학습 언어에 따라 성능 상이 | 형태소 분석기만 있으면 모든 언어 적용 가능 |
| **대표 활용 사례** | Dense Retrieval, 의미 검색, RAG 임베딩 | BM25 키워드 검색, 전통적 정보 검색(IR) |



## 유사도검색
### Cosine Similarity (코사인 유사도)
- 두 벡터가 이루는 각도의 코사인 값(벡터 크기 무관, 방향의 유사도)
- 사용이유: 길이가 다른 텍스트 간에 공정한 유사도 측정 비교 가능하고 결과 -1~1로 고정되어 해석이 쉬움
- 수식

$$
벡터 A = \\(a_1, a_2, ... ,a_n)
$$
$$
‖A‖ = \sqrt{a_1^2 + a_2^2 + \cdots + a_n^2}
$$
$$
‖A‖ = \sqrt{\sum_{i=1}^{n} a_i^2}
$$
$$
cosine similarity(A, B) = \frac{(A · B)}{(‖A‖ × ‖B‖)}
$$

## 벡터 저장과 검색
### Vector Database(벡터 데이터베이스)
- 벡터를 저장하고, 유사도 기반의 근사 최근접 이웃(ANN) 검색을 수행하는 특수 목적 데이터베이스
- 벡터간 유사도 검색 속도를 높이는 자료구조(HNSW)
- RDB와 차이점: RDB는 키워드와 정확히 일치 검색, VDB는 키워드와 유사도 top-k 개 검색
- 대표 제품
  -   Chroma, Qdrant, Pinecone
### HNSW
- 벡터 데이터를 여러 층의 그래프로 구성, 상위 층에서 하위 층으로 내려가면서 탐색 범위를 좁혀가며 가장 유사한 벡터를 찾는 인덱스 알고리즘
   
### ChromaDB
- 임베딩 벡터와 메타데이터를 함께 저장하는 오픈소스 경량 벡터 데이터베이스
- 프롬프트에넣기 위해서 **문서 원문, 임베딩 벡터, 메타 데이터** 저장
- URL
  - https://www.trychroma.com/ 


## 검색과 생성
### Retrieval(검색)
- 파이프 라인
  사용자의 질문 입력 -> 질문 임베딩 -> 유사도 검색 -> top-k 개 문서 -> Generation 전달
### Generation(생성)
- 파이프 라인
  Retrieval 결과 입력 -> 프롬프트 구성 -> LLM 호출 -> 답변 생성 -> 사용자에게 답변 출력

### Context Window (컨텍스트 윈도우)
- 모델이 한 번에 처리할 수 있는 전체 토큰량
- LLM에게 전달할 수 있는 정보의 총량 제한됨(프롬프트,문서,질문,답변의 총 토큰량)
  - 제한 이유(크게 설정하면 되지 않은가?)
    - 과금 비용이 높아짐
    - 입력이 길수록 어텐션(attention)이 분산되서 "Lost in the Middle"(중간 정보를 놓치는 문제) 발생   

### prompt 엔지니어링
- 검색된 문서를 근거로만 답변하도록 지시, 환각을 줄이며, 출처를 명시하도록 유도하는 RAG 전용 프롬프트 설계 기법
- 사용이유: 답변의 정확도와 충실도 상승, 환각률 감소로 인한 답변 신뢰도 상승


## 금일 한줄정리: 
RAG는 질문한 시점에 외부에 저장한 데이터문서 중 필요한 정보를 찾아서, 프롬프트의 입력에 함께 넣어 기존 정보와 함께 답병을 생성하는 방식입니다. RAG의 파이프라인은 **인덱싱단계**와 **질의단계**로 구성됩니다. 인덱싱단계는 원본 문서를 불러오는 ""데이터 로딩"" 단계, 불러온 문서를 작은 단위인 청크로 분할하는 "청킹"단계, 
청크를 임베딩하여 의미 벡터로 변환하는 임베딩단계, 임베딩 벡터와 원본 텍스트를 함께 저장하는 벡터스토어 단계로 순차적 구성됩니다. 질의단계는 질문을 벡터화하고 벡터 저장소에서 관련 문서 청크를 검색하는 리트리벌 단계, 찾은 문서 청크를 프롬프트 입력에 넣는 아규먼테이션 단계, 문서를 근거로 답변을 생성하는 제네레이션단계로 구성됩니다.
 벡터 DB는 인덱싱 단계에서 문서를 청킹하고 임베딩한 벡터를 원문과 함께 저장하는 저장소이며, 질의단계에서는 저장된 벡터중 벡터화된 질문과 유사한 벡터를 검색합니다. 
사용이유는 검색시 그래프기반 근사 최근접 이웃(ANN) 탐색 알고리즘인 **HNSW**을 사용해서 문서 수가 늘어나도, 검색속도가 유지되어 실시간 서비스가 가능합니다.
 ChromaDB는 프롬프트에넣기 위해서 **원문, 벡터, 메타 데이터** 저장하는 오픈소스 라이브러리입니다.
 청킹은 분할기준에 따라 구현복잡도, 임베딩 계산 등이 변하며, 적절한 분할방식에 따라 RAG의 답변 정확도를 높일 수 있습니다.
 컨텍스트 윈도우는 LLM이 한번에 허용하는 처리가능한 최대 토큰, 즉 단어의 수입니다. 해당 토큰을 초과하면 입력이 잘리거나 에러가발생합니다.
그래서 각 단계에서 사용되는 토큰수의 합이 컨텍스트 윈도우를 넘지않게 관리해야합니다.
