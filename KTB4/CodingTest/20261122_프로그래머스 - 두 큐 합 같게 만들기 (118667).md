## 1. 문제 요약 및 제약 조건

### 문제 요약
- 길이가 같은 두 큐 `queue1`, `queue2`가 주어진다.
- 한 번의 작업 = 한쪽 큐에서 `pop`한 원소를 다른 쪽 큐에 `insert`하는 것.
- 두 큐의 원소 합을 **같게** 만드는 데 필요한 **최소 작업 횟수**를 구한다. 불가능하면 `-1`.

### 제약 조건
- 각 큐의 길이: **최대 300,000 (30만)**
- 각 원소의 크기: **최대 1,000,000,000 (10억)**

---

## 2. 고민 과정 및 코드의 발전

### ❌ 1단계: 매번 `sum()` 다시 계산 (시간 초과)

```python
from collections import deque
def solution(queue1, queue2):
    answer = 0
    queue1, queue2 = deque(queue1), deque(queue2)
    target = (sum(queue1) + sum(queue2)) // 2
    if max(max(queue1), max(queue2)) > target:
        return -1
    while sum(queue1) != target:
        if sum(queue1) < target:
            now = queue2.popleft()
            queue1.append(now)
        else:
            now = queue1.popleft()
            queue2.append(now)
        answer+=1
    return answer
```

- **아이디어**: 합이 작은 쪽이 큰 쪽에서 하나 가져온다. (방향은 맞음)
- **문제점**:
  1. **시간 초과**: `sum(queue1)`은 호출할 때마다 큐 전체를 더한다(O(n)). 매 반복마다 두 번 부르므로 30만 × 10만 번 이동이면 수백억 번 연산이 된다.
  2. **무한 루프**: 만들 수 없는 경우(`[3,3]`, `[3,5]`) 멈추는 조건이 없다.
  3. **전체 합이 홀수**: `// 2`가 버림이라 `[1,1]`, `[1,2]`에서 target이 2가 되고, `0`을 반환한다. 정답은 `-1`.

### ⭕ 2단계: 합을 변수로 관리 + 홀수 체크 + 이동 횟수 상한 (제출 통과)

```python
"""
두 큐의 합 확인
낮은쪽에 높은쪽 합 더하기-> 과연 이게 최선일까?
-> 타임 아웃발생
"""
from collections import deque
def solution(queue1, queue2):
    answer = 0
    queue1, queue2 = deque(queue1), deque(queue2)
    sum1 = sum(queue1)
    sum2 = sum(queue2)
    target = sum1 + sum2 
    if max(max(queue1), max(queue2)) > target//2 or target % 2 == 1:
        return -1
    target//=2
    
    length = len(queue1) + len(queue2)
    while sum1 != target and answer <= length:
        
        if sum1 < target:
            now = queue2.popleft()
            queue1.append(now)
            sum1+=now
            sum2-=now
        else:
            now = queue1.popleft()
            queue2.append(now)
            sum1-=now
            sum2+=now
        answer+=1
        
    if sum1 != target:
        return -1
    
    return answer
```

- `sum1`을 들고 있으면서 옮길 때마다 더하고 빼기만 한다 → 한 번 이동이 O(1).
- 전체 합이 홀수면 바로 `-1`.
- 이동 횟수에 상한을 두고, **상한에 걸려 끝나면 `-1`**을 반환한다. 처음에는 상한에 걸려도 `answer`를 그대로 반환해서, 만들 수 없는 경우에 `-1` 대신 이동 횟수가 나왔다.

### 🔧 3단계: 상한을 3n으로 보완 (채점 데이터엔 없지만 틀리는 경우)

2단계 코드는 프로그래머스에서 통과했지만, 상한 `length`(= 2n)로는 부족한 경우가 있다.

```text
queue1 = [1, 1, 1, 1, 1], queue2 = [1, 1, 1, 9, 1]  →  정답 12, 2단계 코드는 -1
```

```python
    limit = len(queue1) * 3          # 최악의 경우 3n - 3번 이동
    while sum1 != target and answer < limit:
```

## 3. 핵심 아이디어 및 원리 분석

### 💡 1. 욕심(그리디) + 투 포인터
- 두 큐를 이어 붙이면 `queue1`은 항상 **이어 붙인 배열의 연속 구간**이다. (앞에서 빼고 뒤에 붙이므로)
- 합이 작으면 구간을 오른쪽으로 늘리고, 크면 왼쪽을 줄인다. **연속된 부분 수열의 합(178870)**과 같은 투 포인터 구조다.
- 원소가 모두 양수라 이 방법이 최소 횟수를 보장한다.

```text
queue1 = [3, 2, 7, 2], queue2 = [4, 6, 5, 1], target = 15

이어 붙인 배열:  3  2  7  2 | 4  6  5  1
처음 queue1:    [3  2  7  2]              합 14 < 15 → 4 가져오기
1번 후:         [3  2  7  2  4]           합 18 > 15 → 3 내보내기
2번 후:            [2  7  2  4]           합 15 ✅ → 정답 2
```

### 💡 2. 이동 횟수 상한은 왜 3n인가 (n = 큐 하나의 길이)
최악은 정답 구간이 **원래 `queue2` 안쪽**에 있을 때다.

| 단계 | 하는 일 | 최대 횟수 | `[1,1,1,1,1]`, `[1,1,1,9,1]` |
|---|---|---|---|
| ① | `queue2`에서 정답 구간 끝까지 가져오기 | n - 1 | 4번 (1, 1, 1, 9) |
| ② | 원래 `queue1`의 원소를 모두 내보내기 | n | 5번 |
| ③ | ①에서 가져온 것 중 정답 구간 앞부분 다시 내보내기 | n - 2 | 3번 (1, 1, 1) |
| 합계 | | **3n - 3** | **12번** |

- 이보다 더 움직이면 한 바퀴를 돌아 같은 상태를 반복하는 것이므로 답이 없다.
- 랜덤 입력 200,000개로 확인: n = 2~7에서 실제 최대 이동 수가 정확히 3n - 3이었고, 상한 2n은 1,435개 오답, 상한 3n은 0개 오답.
- 다른 풀이에서 `len(queue1) * 4`처럼 더 넉넉히 잡아도 O(n)이라 속도 차이는 없다.

## 4. 디버깅 & 실수했던 포인트 정리

1. **반복문 안의 `sum()`**:
   - `sum()`은 O(n)이다. 조건문에 넣으면 반복마다 전체를 다시 더해 O(n²)이 된다.
   - 값이 조금씩만 바뀌면 **합을 변수로 들고 다니며 차이만 반영**한다.
2. **`// 2` 전에 홀수 확인**:
   - 전체 합이 홀수면 반으로 나눌 수 없다. `//`가 조용히 버림을 해서 틀린 target이 만들어진다.
3. **while이 끝난 이유 확인**:
   - "합이 맞아서"와 "상한에 걸려서" 두 경우가 있으므로, 끝난 뒤 `sum1 == target`인지 다시 확인해야 한다.
4. **상한은 최악의 경우를 직접 세서 정하기**:
   - 2n은 "각 원소가 한 번씩 움직인다"는 직관이지만, `queue2`에서 가져온 원소가 다시 나가는 경우를 빠뜨렸다.
   - 채점 데이터에 없어서 통과했을 뿐, 반례가 있었다.

---

## 5. 복잡도 분석

- **시간 복잡도**: $O(n)$
  - 처음 `sum()` 두 번 O(n) + 최대 3n번 이동, 각 이동 O(1) (`deque.popleft()`, `append()`).
- **공간 복잡도**: $O(n)$
  - 두 큐를 `deque`로 바꿔 저장.

## 6. 결론 및 배운 점
- 처음 떠올린 "작은 쪽이 가져오기"는 맞는 방향이었다. 시간 초과의 원인은 알고리즘이 아니라 **반복문 안의 `sum()`**이었다.
- 두 큐를 이어 붙이면 **연속 구간 합 = 투 포인터** 문제로 바뀐다. 어제 푼 연속된 부분 수열의 합(178870)과 같은 구조다.
- "답이 없으면 -1"인 시뮬레이션은 **언제 멈출지(상한)**를 최악의 경우로 계산해서 정해야 한다. 통과했다고 끝내지 말고 반례를 한 번 더 생각해 보자.
