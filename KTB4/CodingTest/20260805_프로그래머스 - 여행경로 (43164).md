# 프로그래머스 - 여행경로 (43164) 풀이 정리

문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/43164

## 문제 요약
- `ICN`에서 출발해서, 주어진 편도 티켓(`tickets`)을 **모두 사용**하는 여행 경로를 찾는다.
- 가능한 경로가 여러 개라면 **알파벳 순서로 가장 앞서는 경로**를 반환한다.
- 항상 모든 티켓을 다 쓰는 경로가 존재한다는 조건이 주어지므로, "경로를 못 찾는 경우"는 고려하지 않아도 된다.

## 아이디어
- 티켓을 `[출발지, 도착지]` 쌍의 2중 리스트로 보고, 이 중 아직 쓰지 않은 티켓들을 골라가며 모든 티켓을 소진하는 경로를 탐색한다.
- 여러 경로 중 알파벳 순으로 가장 앞선 것을 골라야 하므로, 탐색을 시작하기 전에 `tickets.sort()`로 미리 정렬해둔다. 그러면 DFS에서 매번 앞에서부터(알파벳 순으로) 티켓을 선택하게 되어, 가장 먼저 완성되는 경로가 자연스럽게 알파벳 순 최우선 경로가 된다.
- `visited` 배열로 각 티켓의 사용 여부를 추적한다. 같은 도시 쌍이 여러 번 등장할 수 있으므로, 도시 이름이 아니라 **티켓의 인덱스** 단위로 방문 여부를 관리해야 한다.
- `dfs(start, used)`는 "현재 `start` 공항에 있고, 지금까지 `used`개의 티켓을 사용한 상태"를 의미한다. `used`가 전체 티켓 수와 같아지면 모든 티켓을 다 쓴 것이므로 종료 조건으로 `True`를 반환한다.

## 처음에 겪었던 문제
DFS로 접근하는 방향 자체는 처음부터 맞았지만, 이를 **반복문(스택을 직접 관리하는 방식)**으로 구현하려다가 로직이 꼬였다. 어떤 티켓을 방문 취소(백트래킹)해야 하는지, 어느 시점에 경로에 추가/제거해야 하는지를 반복문으로 관리하는 게 까다로웠다. 결국 재귀로 다시 구현해서 해결했지만, 왜 재귀 방식이 이 문제에서 자연스럽게 맞아떨어지는지는 아직 완전히 이해되지 않은 상태다.

## 재귀가 동작하는 이유 (백트래킹 구조)
이 코드의 핵심은 "일단 깊이 끝까지 가보고, 안 되면 되돌아와서 다른 선택지를 시도한다"는 백트래킹이다. 재귀 함수 호출 자체가 이 되돌아오는 과정을 자동으로 처리해준다.

- `dfs(t[1], used+1)`을 호출해서 다음 공항으로 더 깊이 들어가 본다.
- 그 결과가 `True`(끝까지 모든 티켓을 다 썼다)라면, 지금 선택한 티켓의 도착지(`t[1]`)를 `answer`에 추가하고 `True`를 그대로 위로 반환한다. 이 반환이 재귀 호출 스택을 타고 올라가면서, **경로의 마지막 도시부터 역순으로** `answer`에 쌓인다.
- 반대로 `False`가 나오면(그 선택으로는 모든 티켓을 다 못 쓴다는 뜻), `visited[idx] = False`로 되돌리고 다음 티켓 후보를 시도한다. 이게 바로 "잘못된 선택을 취소하고 다른 경우의 수를 시도"하는 백트래킹이다.
- 함수 호출이 끝나고 되돌아올 때마다 그 지점의 지역 변수(`start`, `used`, `for` 루프의 `idx`)는 자동으로 이전 상태로 복원된다. 반복문으로 직접 구현하려면 이 되돌리기(스택에 상태를 저장하고 복원하는 과정)를 전부 손으로 관리해야 하지만, 재귀는 함수 호출 스택이 이 역할을 대신 해준다.
- 마지막에 `answer.append("ICN")` 후 `answer.reverse()`를 하는 이유도 같은 맥락이다. 재귀가 도착지부터 거꾸로 쌓았기 때문에, 시작점을 맨 뒤에 넣고 뒤집어야 정방향 경로가 완성된다.

정리하면, 반복문으로 이 로직을 구현하려면 "지금까지 방문한 순서", "각 단계에서 다음에 시도할 티켓 인덱스" 같은 상태를 전부 별도의 스택 자료구조로 직접 관리해야 하는데, 재귀는 이걸 함수 호출 스택이 자동으로 처리해주기 때문에 훨씬 자연스럽게 표현된다.

## 복잡도
- 최악의 경우 각 단계에서 남은 티켓을 모두 후보로 검토할 수 있어 지수적인 경우의 수가 생길 수 있지만, 정답 경로를 찾는 즉시 `True`를 반환하며 재귀를 즉시 종료(가지치기)하기 때문에 실제로는 훨씬 적은 탐색으로 끝난다.
- 티켓 개수를 `m`이라 하면, 정렬에 O(m log m), DFS 탐색은 문제 조건(항상 해가 존재)하에서 실질적으로 빠르게 종료된다.

## 배운 점
- "여러 후보 중 하나를 시도했다가 실패하면 되돌리고 다른 후보를 시도한다"는 백트래킹 문제는 재귀로 구현하면 상태 복원이 함수 호출 스택을 통해 자동으로 이루어져 훨씬 단순해진다. 반복문으로 직접 구현하려면 이 복원 과정을 전부 수동으로 관리해야 해서 로직이 꼬이기 쉽다.
- 재귀 함수가 `True`를 반환하며 위로 전파될 때, 그 과정에서 결과를 함께 쌓아 올리는(`answer.append`) 패턴은 "경로를 거꾸로 완성해서 마지막에 뒤집는" 방식으로 자주 쓰인다.
- 같은 도시 쌍의 티켓이 여러 장 있을 수 있는 문제에서는, 도시 이름이 아니라 티켓의 인덱스 단위로 방문 여부를 관리해야 정확하다.

## 재귀 깊이 관련 - 왜 이 문제는 RecursionError가 안 나는가
- 이 코드의 재귀 깊이는 최대 `티켓 개수 + 1`이다. 파이썬 기본 재귀 제한(`sys.getrecursionlimit()`)은 보통 1,000이라, 재귀 깊이가 이를 넘으면 메모리 초과보다 먼저 `RecursionError`가 발생한다.
- 문제의 공식 제한사항("공항 수 3~10,000개")은 티켓 개수 자체를 직접 제한하지 않는다. 이 문제는 LeetCode의 "Reconstruct Itinerary" 데이터셋을 가져온 것으로 알려져 있고, 실제 채점 테스트 케이스의 티켓 개수는 재귀 제한(1,000)에 훨씬 못 미치는 수백 개 수준이라 안전하게 통과한다.
- 만약 실제로 티켓이 수천~수만 개까지 주어지는 문제였다면, `sys.setrecursionlimit()`로 제한을 올리거나 반복문 기반 DFS로 바꿔야 안전하다.

## 재귀 버전 vs 반복문 버전

### 왜 재귀가 자연스럽게 동작하는가 (백트래킹 구조)
이 코드의 핵심은 "일단 깊이 끝까지 가보고, 안 되면 되돌아와서 다른 선택지를 시도한다"는 백트래킹이다. 재귀 함수 호출 자체가 이 되돌아오는 과정을 자동으로 처리해준다.

- `dfs(t[1], used+1)`을 호출해서 다음 공항으로 더 깊이 들어가 본다.
- 그 결과가 `True`(끝까지 모든 티켓을 다 썼다)라면, 지금 선택한 티켓의 도착지(`t[1]`)를 `answer`에 추가하고 `True`를 그대로 위로 반환한다. 이 반환이 재귀 호출 스택을 타고 올라가면서, **경로의 마지막 도시부터 역순으로** `answer`에 쌓인다.
- 반대로 `False`가 나오면 `visited[idx] = False`로 되돌리고 다음 티켓 후보를 시도한다. 이게 백트래킹이다.
- 함수 호출이 끝나고 되돌아올 때마다 그 지점의 지역 변수(`start`, `used`, `for` 루프의 `idx`)는 자동으로 이전 상태로 복원된다. 이 복원을 반복문으로 직접 구현하려면 별도의 스택 자료구조로 관리해야 한다.
- 마지막에 `answer.append("ICN")` 후 `answer.reverse()`를 하는 이유도 같은 맥락이다. 재귀가 도착지부터 거꾸로 쌓았기 때문에, 시작점을 맨 뒤에 넣고 뒤집어야 정방향 경로가 완성된다.

### 반복문으로 옮길 때의 설계
재귀가 자동으로 관리해주던 함수 프레임 정보를 직접 스택에 담아야 한다. 각 프레임에는 세 가지가 필요하다.
1. 지금 있는 공항(`node`)
2. `for` 루프가 어디까지 탐색했는지 (다음에 이어서 볼 인덱스)
3. 이 지점에 오기 위해 사용한 티켓의 인덱스 (실패해서 되돌아갈 때 `visited`를 다시 `False`로 풀어줘야 하므로)

이 세 가지를 리스트로 묶어 `stack`에 쌓고, 프레임이 `pop`될 때 3번 정보로 `visited`를 되돌리는 방식으로 재귀와 동일하게 동작시킨다.

### 재귀 ↔ 반복문 대응표

| 재귀 버전 | 반복문 버전 |
|---|---|
| 함수 호출 프레임 (`start`, `used`, `for`의 `idx` 진행 상태) | `stack`에 쌓이는 `[node, next_idx, used_idx]` 리스트 |
| `dfs(t[1], used+1)` 호출 | `stack.append([...])` |
| `return`으로 함수가 종료되며 자동 복귀 | `stack.pop()` |
| 실패 후 `visited[idx] = False`로 되돌리기 | `pop`된 프레임의 `used_idx`로 `visited`를 되돌림 |
| `for` 루프가 다음 반복으로 넘어감 (탐색 이어가기) | `stack[-1][1] = matched + 1`로 다음 탐색 시작점 기억 |

재귀에서는 `for` 루프가 실패할 때마다 `visited[idx] = False`로 되돌리고 **같은 함수 프레임 안에서 계속 다음 후보를 시도**한다. 반복문 버전에서는 현재 프레임에서 후보를 못 찾았을 때만 `pop`해서 상위로 올라가고, 후보를 찾으면 새 프레임을 `push`하는 식으로 나눠서 처리해야 한다. 이 "언제 pop하고 언제 push할지"를 구분하는 것이 반복문으로 짤 때 가장 헷갈리는 지점이며, 처음 반복문으로 시도했다가 꼬였던 부분도 이 지점이었을 가능성이 높다.

로직 자체는 재귀와 반복문 두 버전이 완전히 동일하고 결과도 같다. 다만 재귀는 상태 관리(어디까지 탐색했는지, 실패 시 뭘 되돌려야 하는지)를 파이썬 인터프리터가 함수 호출 스택으로 자동 처리해주는 반면, 반복문은 그 스택 역할을 직접 리스트로 흉내 내야 해서 코드가 더 길어진다. 이것이 이런 백트래킹형 DFS 문제에서 재귀 쪽이 훨씬 간결한 이유다.

## 최종 코드 (재귀 버전)

```python
"""
시작점 0 은 "ICN"
편도 티켓 정보
2중리스트로 구현하기
반드시 모든 경로 방문 경우의수만 주어짐 예외 없음
답: ICN 부터 시작해서 모든 공항 순회하는 경로 찾기 -> 여러개인 경우 알파벳 순으로
알파벳 순 -> 즉 연결리스트를 이름순으로 정렬해서 시작
문제 착각
주어진 티켓을 모두 사용하는 순회 방법
DFS로 구현하는거는 맞았으나 반복문으로 풀려다가 꼬임
하지만 다른 사람들이 반복문이아닌 재귀로 해결해서 나도 재귀로 해결함
하지만 아직까지 왜 재귀가 가능한지 모르겠다.
"""
from collections import deque
def solution(tickets):
    answer = []
    length = len(tickets)
    visited = [False for _ in range(length)]
    tickets.sort()

    def dfs(start, used):
        if used == length:
            return True

        for idx, t in enumerate(tickets):
            if t[0] == start and not visited[idx]:
                visited[idx] = True
                if dfs(t[1], used + 1):
                    answer.append(t[1])
                    return True
                visited[idx] = False

    dfs("ICN", 0)
    answer.append("ICN")
    answer.reverse()
    return answer
```

## 최종 코드 (반복문 버전)

```python
def solution(tickets):
    length = len(tickets)
    tickets.sort()
    visited = [False] * length
    path = ["ICN"]
    answer = []

    # 스택 프레임 구조: [현재 위치, 다음 탐색 시작 인덱스, 이 위치로 오면서 사용한 티켓 인덱스]
    stack = [["ICN", 0, -1]]

    while stack:
        node, next_idx, used_idx = stack[-1]

        if len(path) - 1 == length:
            answer = path[:]
            break

        # 재귀의 for문에 해당하는 부분: next_idx부터 이어서 후보 탐색
        matched = None
        for idx in range(next_idx, length):
            t = tickets[idx]
            if t[0] == node and not visited[idx]:
                matched = idx
                break

        if matched is not None:
            # 다음에 이 프레임으로 돌아왔을 때 이어서 볼 위치를 기억해둠
            stack[-1][1] = matched + 1
            visited[matched] = True
            path.append(tickets[matched][1])
            stack.append([tickets[matched][1], 0, matched])
        else:
            # 더 시도할 후보가 없음 -> 백트래킹
            _, _, finished_used_idx = stack.pop()
            path.pop()
            if finished_used_idx != -1:
                visited[finished_used_idx] = False

    return answer
```
