# 프로그래머스 - 가장 긴 팰린드롬 (12904) 풀이 정리

문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/12904

## 문제 요약
- 문자열 `s`가 주어진다.
- `s`의 부분 문자열 중 **앞으로 읽으나 뒤로 읽으나 같은 문자열(팰린드롬)이면서 가장 긴 것의 길이**를 구한다.

## 아이디어
- 가능한 가장 긴 길이(`len(s)`)부터 시작해서 길이를 하나씩 줄여가며, 그 길이의 모든 부분 문자열이 팰린드롬인지 확인한다.
- 처음으로 팰린드롬을 발견하는 순간의 길이가 곧 정답이다. (길이가 긴 것부터 확인하므로 가장 먼저 찾은 팰린드롬이 곧 최장 팰린드롬이다.)

## 시도 1: `"".join(reversed(now))` — 효율성 테스트 1개 실패
```python
if now == "".join(reversed(now)):
```
`reversed(now)`로 문자열을 뒤에서부터 순회하는 이터레이터를 만들고, `"".join(...)`으로 그 이터레이터를 다시 하나의 문자열로 합쳐서 원본과 비교하는 방식이었다. 로직 자체는 정확했지만, 이 방식으로 효율성 테스트 중 하나를 통과하지 못했다.

## 시도 2: `now[::-1]`로 변경 — 해결
```python
if now == now[::-1]:
```
문자열 뒤집기를 슬라이싱(`[::-1]`)으로 바꾸자 시간 제한 안에 통과했다.

## 왜 같은 결과를 내는 코드인데 속도 차이가 나는가 (Big-O가 아니라 상수 배수의 차이)
두 방식 모두 문자열을 뒤집는 데 걸리는 이론적인 시간복잡도는 **O(k)**(k = 뒤집는 문자열의 길이)로 동일하다. 즉 **점근적 복잡도(Big-O) 자체는 차이가 없다.** 차이는 그 O(k) 연산을 파이썬이 내부적으로 어떻게 실행하느냐는 "상수 배수"에서 발생한다.

- `now[::-1]`(슬라이싱): CPython 내부에서 **C 레벨로 최적화된 단일 연산**으로 처리된다. 문자열 전체를 한 번의 최적화된 복사 루프로 뒤집기 때문에, 파이썬 인터프리터의 반복 오버헤드가 거의 없다.
- `"".join(reversed(now))`: `reversed()`가 먼저 역방향 이터레이터 객체를 만들고, `"".join()`이 그 이터레이터를 **한 글자씩 순회하며(Python의 이터레이터 프로토콜을 거치며)** 새 문자열로 조립한다. 슬라이싱처럼 한 번의 특화된 C 루프로 처리되는 게 아니라, 매 글자마다 이터레이터의 `__next__` 호출과 값 처리 과정을 거치기 때문에 오버헤드가 훨씬 크다.

즉, 두 방법 다 이론적으로는 O(n)이지만, `reversed() + join()` 쪽이 실제 실행 시간에서 몇 배 더 느리다. 이 문제처럼 반복 횟수 자체가 매우 많은(뒤에서 설명할 O(n³) 규모) 상황에서는, 한 번의 뒤집기 연산에 붙는 이 상수 배수 차이가 누적되어 전체 실행 시간에 크게 영향을 준다.

## 전체 알고리즘의 시간복잡도 (여전히 O(n³))
슬라이싱으로 바꿨다고 해서 알고리즘 자체의 점근적 복잡도가 낮아진 것은 아니라는 점을 짚어야 한다.

```python
while answer > 1:                          # 최대 n번
    for n in range(length-answer+1):        # 최대 n번
        now = s[n:n+answer]                 # O(길이)
        if now == now[::-1]:                # O(길이)
            return answer
    answer -= 1
```

- 바깥 `while`(길이 후보)과 안쪽 `for`(시작 위치)가 이중으로 최대 n번씩 돌고, 그 안에서 슬라이싱과 뒤집기 비교가 각각 O(길이)만큼 걸리므로, 최악의 경우 여전히 **O(n³)**에 해당하는 알고리즘이다.
- 다만 각 O(길이) 연산의 상수 배수가 슬라이싱 덕분에 크게 줄어들면서, 이 문제의 실제 제약 조건(문자열 길이) 안에서는 시간 제한을 통과할 수 있었던 것이다. 즉 **알고리즘의 근본적인 복잡도 등급을 낮춘 게 아니라, 같은 등급 안에서 실행 속도를 최적화한 것**이다.

## 배운 점
- 같은 시간복잡도(Big-O)를 가진 코드라도, 파이썬 내부에서 C 레벨로 최적화된 연산(슬라이싱 등)을 쓰는지, 아니면 이터레이터/제너레이터를 거쳐 파이썬 레벨에서 반복 처리하는지에 따라 실제 실행 속도가 몇 배씩 차이 날 수 있다.
- 문자열을 뒤집을 때는 `"".join(reversed(s))`보다 `s[::-1]`이 더 빠르다는 것을 실제로 체감했다. 파이썬에서 문자열/리스트를 다룰 때는 가능하면 슬라이싱처럼 C로 구현된 내장 연산을 우선적으로 고려하는 게 좋다.
- 시간초과가 발생했을 때, 항상 알고리즘의 점근적 복잡도(Big-O)만 문제인 것은 아니다. 알고리즘 등급이 동일하더라도 구현 방식에 따른 상수 배수 차이만으로 시간 제한을 통과하거나 못 할 수 있다는 걸 확인했다. 다만 이는 임시방편에 가까우므로, 입력 규모가 더 커질 가능성이 있다면 중심 확장(expand around center, O(n²))이나 DP 같은 근본적인 알고리즘 개선도 함께 고려하는 게 안전하다.

## 최종 코드

```python
from collections import deque
def solution(s):
    answer = len(s)
    length = len(s)

    while answer > 1:

        for n in range(length - answer + 1):
            now = s[n:n + answer]
            if now == now[::-1]:
                return answer
        answer -= 1
    return answer
```
