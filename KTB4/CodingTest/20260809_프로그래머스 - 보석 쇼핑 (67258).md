# 프로그래머스 - 보석 쇼핑 (67258) 풀이 정리

문제 링크: https://school.programmers.co.kr/learn/courses/30/lessons/67258

## 문제 요약
- 진열된 보석들의 목록 `gems`가 주어진다.
- 모든 종류의 보석을 적어도 하나씩 포함하는 **연속 구간** 중, 가장 짧은 구간을 찾는다.
- 구간이 여러 개면 시작 인덱스가 가장 작은 구간을 반환한다 (1-indexed).

## 아이디어
- 종류 수(`types`)를 미리 구해두고, `buy`라는 딕셔너리로 현재 윈도우 안의 보석별 개수를 관리하는 슬라이딩 윈도우 방식이다.
- `right`를 늘려가며 윈도우에 보석을 추가하고, `len(buy) == types`가 되어 모든 종류가 채워지면 `left`를 줄여가며 최소 길이를 갱신한다.
- 조건이 깨질 때까지(어떤 보석의 개수가 0이 될 때까지) 왼쪽을 좁히고, 다시 오른쪽을 늘리는 과정을 반복한다.

## 발생했던 문제

### 1차 시도: `break`로 인한 인덱스 중복 카운트
처음에는 조건을 만족하는 순간 `break`로 늘리는 `while`문을 빠져나갔는데, 이때 `right += 1`이 실행되지 않아 `right`가 이미 처리한 인덱스에 멈춰 있었다. 이후 다시 늘리는 `while`문에 진입하면 같은 인덱스의 보석을 `buy`에 한 번 더 추가하게 되어, 실제 윈도우 안의 개수보다 부풀려진 값으로 이후 판정이 전부 틀어졌다.

### 2차 시도: `break` 제거 후에도 실패 — `right`의 의미 불일치
`break`는 없앴지만, 더 근본적인 문제가 남아있었다. 늘리는 `while`문에서는 조건을 체크한 직후 `right += 1`이 실행되기 때문에, 그 루프를 빠져나온 시점의 `right`는 "실제로 윈도우에 포함된 마지막 인덱스"가 아니라 **"그 인덱스 + 1"**이었다. 그런데 줄이는 `while`문에서도 이 `right`를 그대로 "마지막 포함 인덱스"인 것처럼 사용해서, 실제로는 윈도우에 없는 인덱스까지 `answer`에 저장하는 문제가 있었다.

추가로 `answer[1] - answer[0]`이라는 인덱스 차이를 길이 대신 사용하고 있었는데, 이는 실제 길이보다 항상 1 작은 값이라 새로운 길이(`right - left`, `right - left + 1` 등)와 일관성 없이 비교되는 문제도 있었다.

### 3차 시도: `right - left`로 통일했지만 여전히 실패
비교 기준을 `right - left`로 통일했지만, 줄이는 `while`문 안에서 여전히 `right`를 그대로 사용하고 있어서 문제가 남아있었다. 예제 `["DIA","RUBY","RUBY","DIA","DIA","EMERALD","SAPPHIRE","DIA"]`를 손으로 추적해보면, 정답이 `[3,7]`이어야 하는데 `[3,8]`처럼 오른쪽 경계가 실제보다 하나 더 크게 저장되는 결과가 나왔다.

## 해결 방법
줄이는 `while`문 안에서는 "실제 윈도우의 마지막 인덱스"가 `right`가 아니라 **`right - 1`**이라는 점을 명시적으로 반영했다.

```
if len(buy) == types and answer[1] - answer[0] > (right - 1) - left:
    answer = [left, right - 1]
```

이렇게 늘리는 while과 줄이는 while 양쪽에서 `answer`에 저장되는 오른쪽 경계의 의미를 "실제로 윈도우에 포함된 마지막 인덱스"로 통일시키자 문제가 해결됐다.

## 복잡도
- `left`와 `right`가 각각 배열을 한 번씩만 순회하며 서로 되돌아가지 않으므로, 전체 시간복잡도는 **O(n)**이다.
- 공간복잡도는 O(k) (`buy` 딕셔너리, k = 보석 종류 수)이다.

## 배운 점
- 슬라이딩 윈도우에서 `right`처럼 반복적으로 증가하는 변수는, 코드의 위치에 따라 "마지막으로 포함된 인덱스"인지 "다음에 처리할 인덱스"인지 그 의미가 미묘하게 달라질 수 있다. 하나의 변수를 서로 다른 두 구간(늘리는 루프, 줄이는 루프)에서 재사용할 때는 그 시점의 정확한 의미를 매번 확인해야 한다.
- `answer[1] - answer[0]` 같은 인덱스 차이를 길이 대신 사용하면, off-by-one 오차가 계속 따라다니며 디버깅을 어렵게 만든다. 길이를 별도의 변수(`min_length` 등)로 명확히 관리하는 편이 훨씬 안전하다.
- `break`로 루프를 빠져나갈 때는, 그 직후에 실행되어야 했던 증감 연산(`right += 1` 등)이 생략된다는 점을 놓치기 쉽다. 자연스럽게 루프 조건에 의해 종료되도록 코드를 짜는 편이 이런 실수를 줄여준다.

## 최종 코드

```python
def solution(gems):
    answer = [-1, 100000]
    length = len(gems)
    types = len(set(gems))
    buy = dict()
    left, right = 0, 0
    if types == 1:
        return [1, 1]

    while right < length:

        while len(buy) < types and right < length:
            if gems[right] in buy:
                buy[gems[right]] += 1
            else:
                buy[gems[right]] = 1

            if len(buy) == types and answer[1] - answer[0] > right - left:
                answer = [left, right]
            right += 1

        while len(buy) == types and left < right:
            now = gems[left]
            buy[now] -= 1
            left += 1
            if buy[now] == 0:
                del buy[now]
            if len(buy) == types and answer[1] - answer[0] > (right - 1) - left:
                answer = [left, right - 1]

    answer[0] += 1
    answer[1] += 1

    return answer
```
